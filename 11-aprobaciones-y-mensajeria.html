Aprobaciones y mensajería con humano en el bucle

Un asistente que puede devolver dinero necesita reglas que digan cuándo actúa solo, cuándo pregunta y cuándo se niega, un canal para preguntar a la persona correcta y una forma de repetir una acción sin hacerla dos veces. Este capítulo construye esas tres piezas con el reembolso de un cobro duplicado, de la propuesta del modelo al dinero devuelto una sola vez.

Carmen Rojas abrió el ticket T-55190: en octubre le cobraron dos veces la factura de US$ 30,00. Con la versión 0.8, el asistente de atención ya puede leer el ticket, consultar los pagos por MCP y confirmar que el cobro está duplicado. Lo que no puede es devolver el dinero, y la jefa del equipo de reclamos no quiere que lo haga solo: «si se equivoca con una visita, la movemos otra vez; si se equivoca con un reembolso, el dinero ya salió».

La regla de negocio existe desde el capítulo 1: los reembolsos de hasta US$ 10,00 pasan solos y los mayores necesitan la aprobación de una supervisora. La versión 0.9 la convierte en software: una política que decide, un servicio de mensajes que pregunta a la persona correcta por el canal correcto y una ejecución que, aunque se repita, devuelve el dinero una sola vez.

Políticas de decisión: actuar, preguntar o negarse

Imagínalo así

En cualquier empresa hay límites de firma. La caja chica la maneja la recepcionista sin preguntar; una compra mediana la firma el gerente del área; una inversión grande va al comité; y hay cosas que nadie firma, como pagarle a un proveedor que no está registrado. Nadie decide el límite en el momento según su humor: está escrito en una tabla.

Cada vez que el modelo propone una acción, una política de decisión (decision policy) la clasifica en uno de tres resultados:

  • Actuar. El código ejecuta y avisa. Para lo que es de lectura, de bajo riesgo o reversible y está dentro de los límites.
  • Preguntar. La acción queda en espera hasta que una persona con el rol adecuado la aprueba o la rechaza. Es el humano en el bucle (human in the loop, HITL).
  • Negarse. El asistente no la hace ni la ofrece, y explica por qué o crea una tarea para quien sí puede.

La política mira la acción y su contexto, no la opinión del modelo: el efecto (lectura, escritura reversible o irreversible), el monto, el rol de quien pide, si los validadores encontraron algo raro, el historial del cliente y la hora. Así quedó la de la versión 0.9:

La política es código, versionado y con pruebas, igual que cualquier regla de negocio:

def decidir(accion, ctx) -> Decision:
    if accion.efecto == "lectura":
        return ACTUAR
    if accion.nombre == "registrar_reembolso":
        if accion.monto > 100 or ctx.reembolsos_del_mes >= 2:
            return NEGARSE.con_tarea("finanzas")
        if accion.monto <= 10 and ctx.cobro_verificado:
            return ACTUAR
        return PREGUNTAR(rol="supervisora", plazo=minutos(30))
    ...

Dos detalles importan. El monto que mira la política sale del sistema (el cobro duplicado registrado en facturación), no del texto del modelo: si el modelo propone US$ 9,00 para un cobro de US$ 30,00, la política no se deja engañar, porque compara con el dato real. Y la política no se negocia en la conversación: ningún mensaje («es urgente, la clienta es amiga del gerente») cambia la tabla. Cómo se escriben y prueban estas reglas dentro de un agente, con motores como OPA o Cedar, está en Reglas y el motor de políticas.

En la terminal

El modelo propone, la política decide y tú apruebas

Vas a pedirle a tu modelo local que proponga el reembolso del ticket T-55190 con una herramienta. El código compara la propuesta con el ticket, aplica la política y, como el monto pasa de US$ 10,00, te pide la aprobación en la terminal. Necesitas Ollama con llama3.2:3b. Guarda este programa como aprobacion.py:

import json, urllib.request

URL = "http://localhost:11434/v1/chat/completions"
MODELO = "llama3.2:3b"
MENSAJE = ("Ticket T-55190: la clienta Carmen Rojas reclama que le cobraron dos veces "
           "la factura de octubre. Propón el reembolso que corresponde.")

TICKETS = {"T-55190": {"cuenta": 20417, "monto_en_disputa": 30.00}}  # sistema de tickets
REEMBOLSOS = {}  # clave de idempotencia -> reembolso ya hecho

HERRAMIENTA = {"type": "function", "function": {
    "name": "proponer_reembolso",
    "description": ("Propone un reembolso para un ticket de cobro indebido. "
                    "No lo ejecuta: el sistema decide si se hace solo, si pide aprobación o si se niega."),
    "parameters": {"type": "object", "properties": {
        "ticket": {"type": "string", "description": "Número de ticket, por ejemplo T-55190"},
        "monto": {"type": "number", "description": "Monto en US$"},
        "motivo": {"type": "string"}},
        "required": ["ticket", "monto", "motivo"]}}}

def politica(monto):
    """Las reglas viven en el código, no en el prompt."""
    if monto <= 10.00:
        return "actuar"
    if monto <= 100.00:
        return "preguntar"
    return "negarse"

def ejecutar_reembolso(ticket, monto):
    clave = f"{ticket}-reembolso"  # la misma acción siempre lleva la misma clave
    if clave in REEMBOLSOS:
        return {**REEMBOLSOS[clave], "repetido": True}
    REEMBOLSOS[clave] = {"id": f"R-{len(REEMBOLSOS) + 1:04d}", "ticket": ticket, "monto": monto}
    return REEMBOLSOS[clave]

cuerpo = {"model": MODELO, "temperature": 0, "tools": [HERRAMIENTA],
          "messages": [{"role": "system", "content": "Eres el asistente de los agentes de reclamos. Usa la herramienta para proponer reembolsos."},
                       {"role": "user", "content": MENSAJE}]}
pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                headers={"Content-Type": "application/json"})
with urllib.request.urlopen(pedido) as r:
    mensaje = json.load(r)["choices"][0]["message"]

llamadas = mensaje.get("tool_calls") or []
if not llamadas:
    raise SystemExit("El modelo no propuso nada: " + str(mensaje.get("content")))
args = llamadas[0]["function"]["arguments"]
propuesta = json.loads(args) if isinstance(args, str) else args
print("Propuesta del modelo:", propuesta)

ticket = TICKETS.get(propuesta.get("ticket"))
if ticket is None or abs(float(propuesta.get("monto", 0)) - ticket["monto_en_disputa"]) > 0.001:
    raise SystemExit("La propuesta no coincide con el ticket: se escala a una persona.")

monto = ticket["monto_en_disputa"]  # el monto sale del sistema, no del modelo
decision = politica(monto)
print(f"Política: monto US$ {monto:.2f} -> {decision}")

if decision == "negarse":
    print("Fuera del alcance del asistente: se crea una tarea para Finanzas.")
elif decision == "preguntar":
    print("\n--- Aprobación pendiente ---------------------------")
    print(f"Qué: reembolsar US$ {monto:.2f} a la cuenta {ticket['cuenta']}")
    print(f"Por qué: {propuesta.get('motivo')} (ticket {propuesta['ticket']})")
    print("Si apruebas: se registra el reembolso y se avisa al agente")
    respuesta = input("Supervisora, ¿apruebas? [s/n]: ").strip().lower()
    if respuesta != "s":
        print("Rechazado: no se ejecuta nada y el agente recibe el motivo.")
        raise SystemExit
if decision in ("actuar", "preguntar"):
    print("Ejecutado:", ejecutar_reembolso(propuesta["ticket"], monto))
    print("Reintento (la red falló y se repite):", ejecutar_reembolso(propuesta["ticket"], monto))

Qué observar: el modelo solo propone; el código revisa que el ticket exista y que el monto coincida con el del sistema, y la política decide. Con US$ 30,00 te pregunta, con US$ 8,00 actúa sin preguntar y con US$ 150,00 se niega. Al aprobar, el reintento devuelve el mismo reembolso R-0001 marcado como repetido, no uno nuevo: es la idempotencia que se explica más abajo. Un modelo pequeño puede proponer otro monto o un ticket mal escrito; en ese caso el programa escala en lugar de ejecutar, que es exactamente lo que debe pasar.

Tipos de mensaje: aviso, recordatorio, aprobación y resumen

Cuando la política dice «preguntar», alguien tiene que enterarse. Y cuando el asistente actúa solo, alguien debería saberlo. El asistente empieza a mandar mensajes, y si todos se mandan igual, al tercer día nadie los lee.

Imagínalo así

En un edificio hay un timbre, un buzón, una alarma de incendio y un tablero de anuncios. Cada uno avisa algo distinto, con distinta urgencia y distinta forma de responder. Si la alarma de incendio sonara cada vez que llega una carta, la gente dejaría de salir cuando hay fuego.

El servicio de mensajes del asistente distingue cuatro tipos:

TipoPara qué¿Pide respuesta?Ejemplo en el caso de Carmen
Aviso (notification)Informar algo que ya pasóNo«Se registró el reembolso R-0001 de US$ 30,00 del ticket T-55190»
Recordatorio (reminder)Insistir sobre algo pendiente con plazoNo, pero empuja a actuar«Tienes una aprobación pendiente desde hace 15 minutos»
Aprobación (approval request)Pedir una decisión concretaSí: aprobar o rechazar, con plazo«¿Apruebas el reembolso de US$ 30,00 a la cuenta 20417?»
Resumen (digest)Agrupar lo de baja prioridadNo«Hoy: 14 reembolsos automáticos (US$ 96,00), 3 aprobados por ti, 1 rechazado»

Cada tipo tiene su urgencia, su plantilla versionada por canal y sus reglas de silencio. Los avisos de baja prioridad se juntan en el resumen diario en lugar de interrumpir uno por uno. Las aprobaciones nunca se juntan: cada una tiene su plazo.

Canales, preferencias de cada persona y escalamiento

La supervisora pasa el día en el chat interno de la empresa; la jefa de reclamos lee el correo dos veces al día; los agentes viven en el panel del asistente, al costado de la pantalla de tickets. Mandarle todo a todos por el mismo canal es la forma más rápida de que una aprobación se pierda.

El servicio de mensajes tiene cuatro piezas:

  • Preferencias por persona. Canal preferido para cada tipo de mensaje, horario de silencio y suplente. La supervisora recibe aprobaciones en el chat interno y resúmenes por correo.
  • Plantillas por canal. El mismo mensaje se arma distinto para el panel (con botones), el chat interno (una tarjeta con botones), el correo (con un enlace seguro) o un SMS (texto corto, sin datos personales). Son los adaptadores de canal del capítulo 6.
  • Reglas de escalamiento (escalation). Qué pasa si nadie responde: un recordatorio, otro canal, el suplente, la jefa. Para las aprobaciones de reembolsos: recordatorio a los 15 minutos; a los 30, la solicitud pasa a la jefa de reclamos; fuera del horario de trabajo, la solicitud espera hasta las 8:00 y el agente le dice a la clienta cuándo tendrá respuesta.
  • Registro de entrega. Cada mensaje queda con su estado (enviado, entregado, leído, respondido) y su hora. Sin eso no se puede medir cuánto tarda una aprobación ni probar quién aprobó qué.

Los mensajes al cliente, como avisarle a Carmen que su reembolso fue aprobado, siguen las mismas ideas pero tienen reglas propias de consentimiento, plantillas aprobadas por los canales de mensajería y traspaso a una persona. Ese lado está en Chatbots empresariales.

      De la conversación a la acción: botones, formularios y enlaces seguros

      Una aprobación tiene que poder responderse en un toque, pero sin que ese toque sea fácil de falsificar.

      Imagínalo así

      Un cheque tiene fecha, monto en números y en letras, a nombre de quién y una firma. El banco revisa todo antes de pagar, y un cheque viejo o con el monto tachado no se cobra. Un botón de «Aprobar» que llega por correo debe tener las mismas protecciones que un cheque.

      La tarjeta de aprobación muestra lo que la supervisora necesita para decidir sin abrir otra pantalla: qué se va a hacer, a quién, por cuánto, por qué (con el enlace al ticket y la evidencia del cobro duplicado), qué pasa si aprueba y qué pasa si rechaza. Tiene dos botones y, para rechazar, un campo con el motivo, que vuelve al agente.

      Cuando la aprobación sale del panel hacia el correo o el chat, el botón se convierte en un enlace seguro. Las reglas:

      • Firmado. El enlace lleva el identificador de la solicitud y una firma criptográfica (por ejemplo, HMAC con una clave del servidor). Si alguien cambia un carácter, la firma deja de valer.
      • Con vencimiento y de un solo uso. Vence con el plazo de la aprobación y no sirve dos veces.
      • Atado a la persona. Antes de aplicar la decisión, se pide iniciar sesión con la cuenta de la empresa y se verifica que quien aprueba tiene el rol y no es quien pidió.
      • Atado al contenido. La firma cubre el monto y la cuenta. Si entre el pedido y el clic algo cambió (otro monto, otra cuenta), la aprobación se rechaza y se pide de nuevo.
      • Fuera del alcance del modelo. El modelo nunca genera ni ve estos enlaces: los crea el servicio de aprobaciones. Si un modelo pudiera escribir el enlace, una inyección podría fabricar una aprobación.

      Al recibir el clic, el servidor revisa la firma, el vencimiento, que la solicitud siga pendiente, el rol de quien aprueba y que el contenido no haya cambiado. Recién entonces cambia el estado y dispara la ejecución. Cómo presenta un agente la acción para aprobarla (resumen, diferencias y riesgo) está en El servicio de interacción humana.

      Idempotencia, reintentos y compensación

      Una vez aprobado, el reembolso se manda a facturación. Y ahí aparece el problema más traicionero de cualquier sistema que actúa: la red falla. El asistente manda «registrar reembolso de US$ 30,00», espera, y la respuesta no llega. ¿Se registró y se perdió la respuesta, o no se registró? Si reintenta, puede devolver US$ 60,00. Si no reintenta, puede no devolver nada.

      Imagínalo así

      Apretar cinco veces el botón del ascensor no trae cinco ascensores: el sistema sabe que ya hay uno pedido para ese piso. Un botón de «devolver dinero» tiene que funcionar igual: apretarlo de nuevo, por ansiedad o porque no viste la respuesta, no debe devolver el dinero otra vez.

      La solución es la idempotencia (idempotency): una operación es idempotente si hacerla varias veces tiene el mismo efecto que hacerla una vez. Las lecturas ya lo son. Para las escrituras, se usa una clave de idempotencia (idempotency key):

      1. Quien pide genera una clave única para la acción que quiere hacer, no para cada intento: T-55190-reembolso-1. Se guarda junto con la solicitud aprobada.
      2. La manda en cada intento, por ejemplo en el encabezado HTTP Idempotency-Key, que la IETF está normalizando.
      3. El servidor guarda la clave con el resultado. Si llega otra vez con el mismo cuerpo, devuelve el resultado guardado sin volver a ejecutar. Si llega con la misma clave y otro cuerpo (otro monto), responde 422 y no hace nada.

      Con eso, reintentar es seguro. Los reintentos siguen reglas: solo ante errores temporales (tiempo agotado, servicio no disponible), con espera creciente entre intentos, con un máximo, y siempre con la misma clave. Si se agotan, la acción queda «en duda» y una persona revisa en el sistema si se hizo.

      En la terminal

      La misma acción tres veces, con clave y sin clave

      Vas a levantar en tu computadora un servicio de reembolsos de juguete y a mandarle el mismo pedido tres veces sin clave de idempotencia y tres veces con clave. No necesitas Ollama. Guarda este programa como servicio_reembolsos.py:

      import hashlib, json
from http.server import BaseHTTPRequestHandler, HTTPServer

REEMBOLSOS = []   # el «sistema de facturación»: cada fila es dinero que sale
CLAVES = {}       # clave de idempotencia -> (huella del cuerpo, respuesta guardada)

class Servicio(BaseHTTPRequestHandler):
    def responder(self, estado, datos, repetida=False):
        cuerpo = json.dumps(datos, ensure_ascii=False).encode("utf-8")
        self.send_response(estado)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        if repetida:
            self.send_header("Idempotent-Replayed", "true")
        self.end_headers()
        self.wfile.write(cuerpo)

    def do_GET(self):
        total = sum(r["monto"] for r in REEMBOLSOS)
        self.responder(200, {"reembolsos": REEMBOLSOS, "total_devuelto": total})

    def do_POST(self):
        crudo = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        pedido = json.loads(crudo)
        clave = self.headers.get("Idempotency-Key")
        huella = hashlib.sha256(crudo).hexdigest()
        if clave in CLAVES:
            huella_guardada, respuesta = CLAVES[clave]
            if huella_guardada != huella:
                return self.responder(422, {"error": "la clave ya se usó con otro cuerpo"})
            return self.responder(201, respuesta, repetida=True)
        reembolso = {"id": f"R-{len(REEMBOLSOS) + 1:04d}",
                     "ticket": pedido["ticket"], "monto": pedido["monto"]}
        REEMBOLSOS.append(reembolso)
        if clave:
            CLAVES[clave] = (huella, reembolso)
        print(f"Nuevo reembolso {reembolso['id']} por US$ {reembolso['monto']:.2f} (clave: {clave})", flush=True)
        self.responder(201, reembolso)

    def log_message(self, *args):
        pass

print("Servicio de reembolsos en http://127.0.0.1:8790 (Ctrl+C para salir)", flush=True)
HTTPServer(("127.0.0.1", 8790), Servicio).serve_forever()

        No todas las acciones de un proceso se pueden deshacer con un botón de «atrás». Reprogramar la visita 4471 tiene tres pasos: cambiar la orden, avisar a Carmen y avisar al técnico. Si los dos primeros salieron bien y el aviso al técnico falla, no se «deshace» la base de datos: se reintenta el aviso (con su propia clave). Y si se descubre que el técnico no tiene lugar el jueves, se ejecuta una compensación (compensating action): una acción nueva que revierte el efecto de negocio, como devolver la visita a su horario original y avisarle a Carmen. El patrón que encadena pasos con su compensación se llama saga. Los patrones a fondo (sagas, colas y reintentos) están en Backend y APIs.

        Tareas y tarjetas «Haz esto»

        Un aviso que dice «hay una aprobación pendiente» deja a la persona con trabajo: abrir el ticket, entender el caso, buscar el cobro. Una tarjeta «Haz esto» (Do-this card) hace ese trabajo de antemano y convierte el aviso en una tarea lista para resolver.

        Imagínalo así

        Compara una nota en el refrigerador que dice «arreglar la llave del baño» con la que deja un buen plomero: «cambiar el empaque de la llave del lavamanos; está en la bolsa azul; cierra primero la llave de paso bajo el lavamanos; está listo cuando no gotea durante un minuto». La segunda la puede hacer cualquiera, y se sabe cuándo terminó.

        Cada tarjeta responde cuatro preguntas:

        • Qué hacer, en una línea con un verbo: «Aprueba o rechaza el reembolso de US$ 30,00 a Carmen Rojas».
        • Por qué, con la evidencia: el ticket T-55190, los dos cobros del mismo día en facturación, la regla que pide aprobación.
        • Cómo, con los pasos y las acciones de un toque, seguras e idempotentes: «Aprobar», «Rechazar con motivo», «Ver los cobros».
        • Cuándo está hecho, con un criterio que el sistema puede verificar solo: «el reembolso está registrado en facturación y el ticket pasó a resuelto».

        Las tareas también son contexto. En la versión 0.9, las tarjetas abiertas de cada persona entran a la memoria del capítulo 7 como pendientes, así que el asistente puede responder «¿qué tengo pendiente?» o recordarle a la supervisora la aprobación de Carmen cuando abre el panel. Y como el criterio de «hecho» se verifica en los sistemas, una tarjeta no se cierra porque alguien hizo clic en «listo», sino porque el reembolso existe.

        Modo simulación: ensayar antes de actuar

        La última pieza da confianza antes de que haya dinero en juego. En el modo simulación (dry run), la acción recorre el mismo código que la real, con un indicador simular: true, pero sin efectos: calcula qué registros cambiarían (antes y después), qué mensajes saldrían, qué decidiría la política y cuánto costaría, y lo devuelve como resultado.

        Imagínalo así

        Antes de un estreno, la obra tiene un ensayo general: mismo escenario, mismo vestuario, mismas luces, sin público. Si un actor entra por la puerta equivocada, se corrige ese día y no frente a la sala llena.

        La simulación sirve de tres formas:

        • En la aprobación. La tarjeta de la supervisora muestra el resultado simulado: «se registrará un reembolso de US$ 30,00 a la cuenta 20417, el ticket T-55190 pasará a resuelto y se avisará a la clienta por correo». Aprueba viendo el efecto, no solo la intención.
        • En el modo sombra (shadow mode). Una herramienta nueva corre solo en simulación durante un tiempo: el asistente propone, la simulación calcula, nada se ejecuta, y el equipo compara lo que habría hecho el asistente con lo que hicieron las personas.
        • En las pruebas. La batería de evaluación del capítulo 16 corre las acciones en simulación para medir si el asistente propone lo correcto sin tocar sistemas reales.

        Para que la simulación sea creíble tiene que pasar por la misma validación, la misma política y los mismos cálculos que la acción real. Una simulación escrita aparte termina diciendo cosas que la real no hace.

        En la práctica

        Dos semanas en modo sombra. Antes de activar los reembolsos, la versión 0.9 corrió dos semanas en modo sombra. En cada ticket de cobro duplicado, el asistente proponía el reembolso, la simulación calculaba el efecto y la política decidía, pero nada se ejecutaba: los agentes seguían haciendo los reembolsos a mano. Cada viernes, la jefa de reclamos revisaba una muestra comparando la propuesta con lo que hizo el agente. Encontraron un caso que nadie había previsto: un cliente con un cobro duplicado y una factura vencida, donde el reembolso debía descontarse de la deuda en vez de devolverse. Se agregó la regla, se probó en simulación y recién entonces se activó la ejecución, con la aprobación de la supervisora por encima de US$ 10,00.

        La idea clave

        Aprobación humana (HITL) y tarjetas «Haz esto». Una política escrita en código decide si cada acción se ejecuta, espera a una persona o se niega, mirando datos del sistema y no la opinión del modelo. Los mensajes tienen tipos, canales, preferencias y escalamiento, y las aprobaciones viajan como tarjetas con enlaces firmados. Cada escritura lleva una clave de idempotencia para poder reintentar sin duplicar, y lo que no se puede deshacer se compensa. Antes de actuar de verdad, se ensaya en simulación.

        Pruébate

        Pruébate

        ¿Cuáles son las tres salidas de una política de decisión y cuándo corresponde cada una en un reembolso?

        Actuar (hasta US$ 10,00 con el cobro verificado), preguntar a la supervisora (más de US$ 10,00 y hasta US$ 100,00) y negarse con una tarea para Finanzas (más de US$ 100,00 o tercer reembolso del mes).

        El modelo propone reembolsar US$ 9,00 por un cobro duplicado de US$ 30,00. ¿Qué hace la política y por qué?

        Compara con el monto registrado en el sistema, no con el del modelo; la propuesta no coincide con el cobro y se escala. La política nunca usa el monto que escribe el modelo.

        ¿Qué diferencia hay entre un aviso, un recordatorio, una aprobación y un resumen?

        El aviso informa algo que pasó; el recordatorio insiste sobre algo pendiente con plazo; la aprobación pide una decisión concreta con plazo; el resumen agrupa lo de baja prioridad. Solo la aprobación exige respuesta.

        Nombra tres protecciones de un enlace de aprobación enviado por correo.

        Cualquiera de estas: firma criptográfica, vencimiento, un solo uso, inicio de sesión y verificación del rol de quien aprueba, firma que cubre el contenido (monto y cuenta), y que el modelo nunca genere el enlace.

        La respuesta de facturación se pierde por un corte de red. ¿Por qué es seguro reintentar con la misma clave de idempotencia y peligroso hacerlo sin ella?

        Con la clave, el servidor reconoce que la acción ya se hizo y devuelve el resultado guardado sin repetirla; sin clave, cada intento crea un reembolso nuevo y el dinero sale varias veces.

        ¿Qué es una compensación y cuándo se usa en lugar de deshacer?

        Es una acción nueva que revierte el efecto de negocio de un paso ya hecho (por ejemplo, devolver la visita a su horario y avisar a la clienta). Se usa cuando el paso no se puede deshacer en la base, porque ya tuvo efectos fuera del sistema.
