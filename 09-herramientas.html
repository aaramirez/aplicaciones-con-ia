Herramientas: el modelo que pide ejecutar funciones

Hasta aquí el asistente lee, recuerda y cita. Para dar el monto real de una factura o mover una visita necesita algo más: pedirle al código que ejecute una función. Este capítulo arma ese ciclo, el contrato de cada herramienta, el registro que las gobierna y la forma de convertir cada parte de la aplicación en una acción que un modelo puede usar.

El asistente de atención llegó a la versión 0.6 con buenas notas. Arma el contexto con los datos de la cuenta, recuerda lo que importa de cada caso y responde con los manuales citando la fuente. La jefa del equipo de reclamos tenía, sin embargo, una queja que se repetía: «me dice qué dice la política, pero el agente igual tiene que abrir facturación para ver cuánto debe Carmen». El asistente sabía las reglas, pero no tenía los datos del momento.

Lucía propuso el siguiente peldaño, el nivel 3: que el asistente pueda pedir datos y acciones a los sistemas de la empresa. Mateo empezó la versión 0.7 con tres herramientas de lectura y una de escritura, y con una regla que no se negocia: el modelo propone, el código decide y ejecuta.

El ciclo: el modelo propone una llamada, el código la ejecuta y devuelve el resultado

Imagínalo así

Un médico no corre los análisis de sangre. Llena una orden de laboratorio con un formato fijo («hemograma, paciente 20417, en ayunas»), el laboratorio la procesa con sus máquinas y le devuelve un informe. El médico lee el informe y decide qué decirle al paciente. Si la orden está mal llenada, el laboratorio la devuelve con una nota, y el médico la corrige. Nunca toca la máquina.

La llamada a herramientas (tool calling, también function calling) funciona igual. En cada pedido al modelo, además de los mensajes, tu código manda la lista de herramientas (tools) disponibles: funciones con un nombre, una descripción y un esquema de lo que reciben. El modelo puede responder de dos maneras: con texto para la persona, o con una o más llamadas a herramientas (tool calls), que son pedidos estructurados del tipo «ejecuta consultar_factura con {"numero": "F-88213"}». En la API compatible con OpenAI, la segunda forma llega en el campo tool_calls del mensaje y el motivo de parada (finish reason) es tool_calls.

El modelo no ejecuta nada. Es tu código el que:

  1. Lee cada llamada, comprueba que la herramienta existe y que los argumentos cumplen el esquema.
  2. Revisa si esa persona, con ese rol, puede hacer eso (los permisos y las aprobaciones están en el capítulo 11).
  3. Ejecuta la función real: una consulta a facturación, un cálculo en el motor de tarifas.
  4. Agrega el resultado a la conversación como un mensaje con el rol tool y el identificador de la llamada (tool_call_id), para que el modelo sepa qué resultado responde a qué pedido.
  5. Vuelve a llamar al modelo con todo lo anterior.

El ciclo se repite hasta que el modelo responde con texto o hasta que el código corta: un tope de vueltas evita que un modelo confundido pida herramientas para siempre. Cada vuelta es una llamada completa al modelo, con todos los mensajes anteriores y todas las definiciones de herramientas, así que cada vuelta suma tokens, costo y latencia.

Este capítulo trata la herramienta como pieza de un producto: su contrato, su registro y su lugar en la arquitectura. El bucle del agente por dentro (los motivos de parada, el streaming de eventos, cómo redirigir un bucle en marcha) es el tema de El bucle del agente, en Cómo construir un arnés.

En la terminal

El ciclo completo con dos herramientas

Vas a darle a tu modelo local dos herramientas (consultar una factura y calcular el total para reconectar) y a ver cómo las pide, cómo las ejecuta el código y cómo responde con el resultado. Necesitas Ollama con llama3.2:3b (capítulo 1), que acepta herramientas por su API compatible con OpenAI. Guarda este programa como herramientas.py:

import json, urllib.request

URL = "http://localhost:11434/v1/chat/completions"
MODELO = "llama3.2:3b"
MENSAJE = ("La clienta de la cuenta 20417 tiene vencida la factura F-88213 "
           "y pide la reconexión. ¿Cuánto paga hoy?")

# Los sistemas de verdad (aquí, datos de ejemplo en memoria)
FACTURAS = {"F-88213": {"cuenta": 20417, "mes": "octubre",
                        "monto": 30.00, "estado": "vencida"}}
RECONEXION = 5.00

def consultar_factura(numero):
    f = FACTURAS.get(numero)
    if f is None:
        return {"error": "factura_no_existe",
                "detalle": f"No hay ninguna factura {numero}. Pide el número correcto."}
    return {"numero": numero, **f}

def calcular_total_reconexion(cuenta):
    vencidas = [f["monto"] for f in FACTURAS.values()
                if f["cuenta"] == cuenta and f["estado"] == "vencida"]
    return {"cuenta": cuenta, "facturas_vencidas": len(vencidas),
            "total": sum(vencidas) + RECONEXION}

FUNCIONES = {"consultar_factura": consultar_factura,
             "calcular_total_reconexion": calcular_total_reconexion}

HERRAMIENTAS = [
    {"type": "function", "function": {
        "name": "consultar_factura",
        "description": ("Devuelve el mes, el monto, la cuenta y el estado de una factura. "
                        "Úsala cuando la persona menciona un número de factura (F-#####)."),
        "parameters": {"type": "object",
                       "properties": {"numero": {"type": "string",
                                                 "description": "Número de factura, por ejemplo F-88213"}},
                       "required": ["numero"]}}},
    {"type": "function", "function": {
        "name": "calcular_total_reconexion",
        "description": ("Calcula cuánto paga una cuenta para reconectar: facturas vencidas "
                        "más el cargo de reconexión. Úsala siempre que pregunten un monto a pagar."),
        "parameters": {"type": "object",
                       "properties": {"cuenta": {"type": "integer",
                                                 "description": "Número de cuenta del cliente"}},
                       "required": ["cuenta"]}}},
]

def llamar(mensajes):
    cuerpo = {"model": MODELO, "temperature": 0,
              "messages": mensajes, "tools": HERRAMIENTAS}
    pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                    headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(pedido) as r:
        return json.load(r)["choices"][0]["message"]

def ejecutar(nombre, args):
    funcion = FUNCIONES.get(nombre)
    if funcion is None:
        return {"error": "herramienta_desconocida", "detalle": nombre}
    try:
        return funcion(**args)
    except TypeError as e:  # argumentos que no calzan con la función
        return {"error": "argumentos_invalidos", "detalle": str(e)}

mensajes = [
    {"role": "system", "content": ("Eres el asistente de los agentes de atención. "
                                   "Usa las herramientas para todo dato o monto; nunca inventes cifras. "
                                   "Responde en español, en una o dos frases.")},
    {"role": "user", "content": MENSAJE},
]

for vuelta in range(1, 5):  # tope de vueltas: nunca un ciclo infinito
    respuesta = llamar(mensajes)
    llamadas = respuesta.get("tool_calls") or []
    if not llamadas:
        print("\nRespuesta final:", respuesta.get("content"))
        break
    mensajes.append(respuesta)
    for llamada in llamadas:
        nombre = llamada["function"]["name"]
        args = llamada["function"]["arguments"]
        if isinstance(args, str):
            args = json.loads(args or "{}")
        print(f"[vuelta {vuelta}] el modelo pide {nombre}({args})")
        resultado = ejecutar(nombre, args)
        print(f"           el código devuelve {resultado}")
        mensajes.append({"role": "tool", "tool_call_id": llamada.get("id", ""),
                         "content": json.dumps(resultado, ensure_ascii=False)})
else:
    print("Se alcanzó el tope de vueltas: se escala a una persona.")

  2. Compara el monto de la respuesta final con el que devolvió calcular_total_reconexion.

Qué observar: el modelo no calcula: pide una o las dos herramientas, el código las ejecuta y el total (US$ 35,00) sale de la función. Los argumentos llegan como JSON que el código decodifica y valida. Sin herramientas, el modelo responde de inmediato y tiene que adivinar el cargo de reconexión. Un modelo pequeño a veces pide una herramienta que no hacía falta, o la misma dos veces; por eso el código tiene un tope de vueltas. El mismo programa sirve con un proveedor comercial cambiando la dirección, el modelo y la clave.

    Definir una herramienta: nombre, descripción y esquema de entrada

    Para el modelo, una herramienta es solo texto: lo que dicen su nombre, su descripción y su esquema. No ve el código. Si la descripción es vaga, elegirá mal; si el esquema es flojo, mandará argumentos que el código no entiende.

    Imagínalo así

    Un formulario de ventanilla bien hecho dice arriba para qué sirve («Solicitud de cambio de domicilio»), aclara cuándo no usarlo («para cambio de titular, use el formulario B») y pone al lado de cada casilla qué va ahí y en qué formato («fecha: DD/MM/AAAA»). Un formulario que solo dice «Datos» recibe cualquier cosa.

    Una definición tiene tres partes:

    • Nombre. Un verbo y un objeto del negocio, en minúsculas y sin espacios: consultar_factura, reprogramar_visita. Que se entienda solo. Evita nombres genéricos (procesar, accion1) y nombres casi iguales entre sí.
    • Descripción. Qué hace, cuándo usarla, cuándo no usarla y qué devuelve. Es, en la práctica, una parte del prompt, y se escribe con el mismo cuidado que las plantillas del capítulo 4.
    • Esquema de entrada (input schema). Un esquema JSON (JSON Schema), como en el capítulo 5: cada parámetro con su tipo, su descripción, sus valores permitidos (enum), su formato (pattern, minimum) y cuáles son obligatorios. additionalProperties: false rechaza campos inventados.

    Así quedó la definición de la herramienta de escritura de la versión 0.7:

    {
  "name": "reprogramar_visita",
  "description": "Cambia el día y la franja de la visita técnica de una orden de trabajo abierta. Úsala solo cuando la persona pide mover una visita ya agendada; para agendar una visita nueva no sirve. Devuelve la orden con su nueva fecha, o un error que explica por qué no se pudo.",
  "parameters": {
    "type": "object",
    "additionalProperties": false,
    "properties": {
      "orden": {"type": "integer", "description": "Número de la orden de trabajo, por ejemplo 4471"},
      "fecha": {"type": "string", "format": "date", "description": "Día nuevo, en formato AAAA-MM-DD"},
      "franja": {"type": "string", "enum": ["manana", "tarde"]}
    },
    "required": ["orden", "fecha", "franja"]
  }
}

    Fíjate en tres decisiones. La fecha va en formato canónico y no como «el jueves», porque el modelo puede traducir «el jueves» a una fecha (sabe la de hoy si se la pones en el contexto) y el código no debería tener que interpretar lenguaje. La franja es una enumeración, no texto libre. Y la descripción dice qué devuelve cuando falla, lo que le enseña al modelo qué hacer con un error.

    El registro de herramientas: metadatos, riesgo, permisos y dueño

    La definición es lo que ve el modelo. El código necesita saber mucho más de cada herramienta, y lo guarda en un registro de herramientas (tool registry): un catálogo versionado, con una ficha por herramienta, que es la fuente de verdad para armar la lista que se manda al modelo y para decidir qué se ejecuta.

    Imagínalo así

    En un hospital, el carro de medicamentos tiene una etiqueta visible en cada cajón (nombre y dosis) y una hoja de control que la enfermera no le lee al paciente: quién puede administrarlo, si requiere doble firma, qué farmacia lo repone y cuándo vence. La etiqueta es la descripción; la hoja de control es el registro.

    IdempotenteSi repetirla con los mismos datos da el mismo efectosí, con clave por orden y fecha

    Con el registro, la lista de herramientas deja de ser fija. Un técnico y un agente de reclamos ven listas distintas, porque cada uno solo recibe las herramientas que su rol permite. Lo que el modelo no conoce, no lo puede pedir, y eso es más seguro que confiar en que «no lo pedirá». Cómo se ejecutan y validan las herramientas dentro de un agente, con su registro de capacidades, está en El runtime de herramientas.

    Cada slice de VSA como herramienta

    ¿De dónde salen las herramientas? La respuesta mala es escribir funciones nuevas «para la IA» junto a la aplicación de siempre, con su propia lógica de negocio. A los tres meses hay dos formas de reprogramar una visita, y cada una valida distinto.

    La respuesta buena aprovecha cómo está construida la aplicación. En una arquitectura de cortes verticales (Vertical Slice Architecture, VSA), cada funcionalidad es un slice (corte) que tiene todo lo suyo: el pedido, la validación, la lógica, el acceso a datos y la respuesta. «Reprogramar visita» es un slice; «consultar factura», otro. La arquitectura a fondo está en Backend y APIs.

    Imagínalo así

    Un banco tiene una sola bóveda y un solo sistema de cuentas, pero dos formas de retirar dinero: la ventanilla y el cajero automático. Las reglas son las mismas (saldo, límite diario, identificación); lo único distinto es por dónde entra el pedido. Nadie construye una segunda bóveda para el cajero.

    Un slice bien hecho ya tiene lo que pide una herramienta: un pedido con esquema, una validación y un resultado estructurado. Solo le falta una segunda puerta. La primera es el endpoint REST que usa la pantalla de órdenes; la segunda es un adaptador de herramienta que traduce el esquema del pedido a la definición que ve el modelo y llama al mismo manejador:

    # slices/reprogramar_visita.py  (esbozo)
class Pedido(BaseModel):            # el mismo esquema para las dos puertas
    orden: int
    fecha: date
    franja: Literal["manana", "tarde"]

def manejar(pedido: Pedido, usuario: Usuario) -> Resultado:
    ...                             # reglas de negocio, una sola vez

# Puerta 1: la pantalla de órdenes
@app.post("/v1/ordenes/{orden}/reprogramacion")
def endpoint(orden: int, cuerpo: Pedido, usuario = Depends(usuario_actual)):
    return manejar(cuerpo, usuario)

# Puerta 2: el asistente
registro.agregar(herramienta_desde(Pedido, nombre="reprogramar_visita",
                                   descripcion=DESCRIPCION, manejar=manejar,
                                   efecto="escritura", riesgo="medio"))

    El adaptador hace tres cosas más: pasa la identidad de la persona que pidió (el asistente actúa en nombre de ella, nunca con permisos propios más amplios), convierte las excepciones en errores con explicación y registra la llamada en la traza. En el capítulo 10, la misma puerta se publica por MCP para que otras aplicaciones la usen.

    Diseñar la aplicación para agentes (agent-ready)

    Una aplicación lista para agentes (agent-ready) es la que ofrece acciones que un modelo puede usar bien. No es otra aplicación: es la misma, diseñada pensando en un usuario nuevo que lee descripciones en vez de mirar botones.

    Imagínalo así

    Un edificio accesible no es un edificio aparte para personas en silla de ruedas: es el mismo edificio con rampas, ascensores con botones a la altura correcta y letreros claros. Al principio parece un costo extra; después todos usan la rampa con el carrito de compras.

    Lo que hace una aplicación agent-ready:

    • Acciones del negocio, no tablas. reprogramar_visita en vez de actualizar_registro(tabla, id, campos). Una acción del negocio trae sus reglas adentro; una actualización genérica deja las reglas en manos del modelo.
    • Buscar antes de actuar. Herramientas de búsqueda (buscar_cliente por nombre) que devuelven identificadores canónicos (la cuenta 20417), y herramientas de acción que solo aceptan esos identificadores. Así el modelo no actúa sobre «la señora Rojas» sin saber cuál.
    • Salidas cortas y estructuradas. Lo que el modelo necesita para seguir, no la ficha completa con 80 campos. Cada token de resultado vuelve a viajar en las vueltas siguientes.
    • Errores que explican. «La orden 4471 ya está cerrada; no se puede reprogramar» le permite al modelo responder bien; «Error 500» no.
    • Simulación. Un parámetro simular: true que devuelve lo que pasaría sin hacerlo. El capítulo 11 lo usa para las aprobaciones.
    • Límites y paginación. Ninguna herramienta devuelve diez mil filas; devuelve las primeras veinte y un cursor.

    El antipatrón más común es la herramienta comodín: ejecutar_sql(consulta) o llamar_api(url, metodo, cuerpo). Parecen flexibles, pero le pasan al modelo todo el poder y toda la responsabilidad, y convierten cualquier texto malicioso que lea en una orden con acceso a la base. El capítulo 10 vuelve sobre esto con el acceso a bases de datos.

    Herramientas de lectura y de escritura

    No todas las herramientas pesan lo mismo. Una herramienta de lectura (read tool) consulta y no cambia nada: si se equivoca, el daño es una respuesta mala o un dato que alguien no debía ver. Una herramienta de escritura (write tool) cambia el estado de un sistema: si se equivoca, hay que deshacer algo, y a veces no se puede.

    La versión 0.7 las separó en tres grupos, con reglas distintas:

    GrupoHerramientasRegla
    Lecturaconsultar_factura, estado_ticket, calcular_total_reconexion, buscar_en_manualesSe ejecutan solas, filtradas por los permisos de quien pregunta
    Escritura reversiblereprogramar_visitaPasa por el motor de políticas; por ahora, con aprobación
    Escritura irreversibleregistrar_reembolsoNunca sola: siempre una persona, con el monto que da el sistema

    calcular_total_reconexion es de lectura aunque «calcula»: no cambia nada, y es justamente la herramienta que cumple la regla del capítulo 2 de que el modelo nunca hace la cuenta final.

    En la práctica

    Primero leer, después escribir. Durante las dos primeras semanas de la versión 0.7, el asistente tuvo solo las herramientas de lectura. Mateo midió dos cosas en las trazas: cuántas veces el modelo pedía la herramienta correcta para la pregunta y cuántas pedía una que no hacía falta. Con esos números, y con la jefa de reclamos revisando una muestra, se habilitó reprogramar_visita detrás de una aprobación. La escritura llegó con evidencia de que el modelo elegía bien, no con la esperanza de que lo hiciera.

    Errores como datos y llamadas en paralelo

    Cuando una herramienta falla, la tentación es lanzar una excepción y cortar todo. En un ciclo con modelo conviene lo contrario: devolver el error como dato (error as data), un resultado normal que dice qué falló y por qué, para que el modelo pueda corregirse o explicarle el problema a la persona.

    Hay tres clases de error, y cada una se trata distinto:

    • Error de entrada. El modelo mandó F-8821 en vez de F-88213. Se devuelve {"error": "factura_no_existe", "detalle": "..."} y el modelo pide el número correcto o prueba otra vez.
    • Error de negocio. La orden ya está cerrada, el monto supera lo permitido. Se devuelve la regla en palabras, para que el modelo la explique.
    • Error del sistema. Facturación no responde. Eso no lo arregla el modelo: el código reintenta con espera creciente y, si sigue fallando, devuelve «el sistema de facturación no está disponible» y el asistente lo dice sin inventar un monto.

    Un modelo también puede pedir varias herramientas en el mismo turno (parallel tool calls): para responder «¿cuánto debe Carmen y en qué va su reclamo?» pide calcular_total_reconexion y estado_ticket a la vez. El código puede ejecutar en paralelo las de lectura, porque no dependen una de otra, y devolver todos los resultados antes de la siguiente vuelta. Las de escritura conviene ejecutarlas una por una y en el orden pedido, porque una puede depender del efecto de otra.

    En la terminal

    Dos herramientas a la vez y un error como dato

    Vas a usar el mismo herramientas.py de la primera práctica con dos pedidos nuevos: uno que pide dos datos a la vez y uno con un número de factura que no existe.

    1. Cambia MENSAJE por «¿De cuánto es la factura F-88213 y cuánto paga la cuenta 20417 para reconectar?» y ejecuta el programa como antes.
    2. Anota si el modelo pidió las dos herramientas en la misma vuelta o en vueltas distintas.
    3. Cambia MENSAJE por «¿De cuánto es la factura F-8821?» y vuelve a correrlo.
    4. En consultar_factura, cambia la línea del error por raise KeyError(numero) y corre el paso 3 otra vez.

    Qué observar: en el paso 1 muchos modelos piden las dos herramientas en una sola vuelta, y el programa ejecuta las dos antes de volver al modelo; otros las piden de a una, y eso cuesta una vuelta más. En el paso 3, la herramienta devuelve el error como dato y el modelo responde que no encuentra la factura o pide el número correcto, sin inventar un monto. En el paso 4 la excepción no la atrapa nadie: el programa se cae y la persona no recibe ninguna respuesta. Ese es el motivo para devolver los errores como datos. Vuelve a dejar la línea como estaba.

    Cuántas herramientas son demasiadas

    Cada herramienta que agregas tiene un costo. Su definición viaja en cada llamada, así que cuarenta herramientas con buenas descripciones pueden sumar varios miles de tokens antes de que el modelo lea la pregunta. Y cada herramienta nueva es una opción más para confundirse: si hay consultar_factura, consultar_factura_electronica y consultar_pagos, la elección entre ellas depende de una palabra.

    Imagínalo así

    Una caja de herramientas con veinte destornilladores casi iguales no te hace mejor carpintero: te hace perder tiempo eligiendo, y a veces eliges el que no calza. El carpintero bueno lleva al trabajo los seis que necesita para ese trabajo.

    No hay un número mágico; depende del modelo y de cuánto se parecen las herramientas entre sí. Lo que sí se observa siempre es que la precisión al elegir baja cuando el catálogo crece y cuando las descripciones se pisan. Las estrategias:

    • Catálogo por rol y por tarea. El asistente de reclamos no necesita las herramientas de inventario. El registro arma la lista según quién pregunta y en qué pantalla está.
    • Selección dinámica. Con catálogos grandes, un paso previo elige las diez herramientas más relevantes para el pedido, con una búsqueda por significado sobre las descripciones (la misma técnica del RAG del capítulo 8), y solo esas viajan al modelo.
    • Consolidar. Tres herramientas que consultan la factura de tres formas pueden ser una con un parámetro.
    • Nombres con prefijo. facturacion.consultar y ordenes.reprogramar separan dominios y evitan choques cuando las herramientas vienen de varios sistemas.

    La idea clave

    Herramientas como funciones con contrato. El modelo propone una llamada con datos estructurados; el código valida, revisa permisos, ejecuta y devuelve el resultado, también cuando es un error. Cada herramienta tiene un nombre del negocio, una descripción que dice cuándo usarla y un esquema estricto, y una ficha en el registro con su riesgo, sus roles y su dueño. Las mejores herramientas no se escriben aparte: son los mismos slices de la aplicación, con una segunda puerta.

    Pruébate

    Pruébate

    En el ciclo de llamada a herramientas, ¿quién ejecuta la función y cómo se entera el modelo del resultado?

    La ejecuta el código de la aplicación, después de validar la llamada y los permisos. El resultado vuelve al modelo como un mensaje con el rol tool y el identificador de la llamada, en la siguiente vuelta.

    ¿Por qué el ciclo necesita un tope de vueltas?

    Porque cada vuelta es una llamada completa al modelo, con costo y latencia, y un modelo confundido puede pedir herramientas una y otra vez sin llegar a una respuesta. Al llegar al tope, se escala a una persona.

    ¿Qué información de una herramienta ve el modelo y cuál queda solo en el registro?

    El modelo ve el nombre, la descripción y el esquema de entrada. El registro guarda además la versión, el efecto, el riesgo, los roles, si pide aprobación, si es idempotente, los límites y el dueño.

    ¿Por qué conviene exponer un slice existente como herramienta en vez de escribir una función nueva para la IA?

    Porque así las reglas de negocio viven en un solo lugar: la pantalla y el asistente pasan por el mismo manejador y la misma validación, y no aparecen dos formas de hacer lo mismo que validan distinto.

    La herramienta consultar_factura recibe un número que no existe. ¿Qué debería devolver y por qué?

    Un resultado normal con el error como dato (por ejemplo, factura_no_existe y una explicación), para que el modelo pida el número correcto o se lo diga a la persona, en lugar de una excepción que corta la conversación.

    ¿Por qué ejecutar_sql(consulta) es una mala herramienta para un asistente?

    Porque traslada al modelo todo el poder y las reglas de negocio, permite cualquier consulta y convierte un texto malicioso en una orden con acceso a la base. Es mejor una acción del negocio con parámetros y permisos.
