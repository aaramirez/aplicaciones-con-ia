Un modelo probabilístico para necesidades deterministas

Pregúntale lo mismo dos veces a un modelo de lenguaje y puede responder distinto. El negocio, en cambio, necesita que una factura sume igual todas las veces. Este capítulo explica de dónde sale la variabilidad y cómo se envuelve el modelo en capas de código para que la empresa pueda confiar en él.

Por qué el mismo pedido da respuestas distintas

Mateo, el desarrollador del asistente de atención, hizo la primera prueba seria un martes. Le pasó al modelo la pregunta «Carmen tiene vencida la factura de octubre, de US$ 30,00, y pide la reconexión: ¿cuánto paga hoy?» veinte veces seguidas. Obtuvo once respuestas distintas. Siete decían US$ 35,00 con distintas palabras, cuatro decían US$ 30,00, dos inventaron un recargo por mora y una respondió «depende de su plan». La jefa del equipo de reclamos lo resumió sin rodeos: «si el sistema de facturación hiciera esto, lo apagamos».

Imagínalo así

Pídele a diez cocineros expertos la misma receta de arroz con pollo y te darán diez platos parecidos, ricos y distintos. Eso está bien en un restaurante. Pero si les pides que pesen exactamente 250 gramos de arroz, quieres que los diez usen la balanza, no el ojo. Un modelo de lenguaje es un cocinero muy bueno que, si no le das balanza, calcula a ojo.

Un modelo de lenguaje no busca una respuesta guardada: la genera palabra por palabra. Más exactamente, genera tokens (tokens), pedazos de palabra con los que el modelo trabaja. En cada paso calcula la probabilidad de cada token posible y elige uno. Si siempre eligiera el más probable, respondería casi igual cada vez; pero por omisión muestrea (sampling): elige al azar, con más chance para los más probables. La temperatura (temperature) es el parámetro que controla cuánto azar hay: con 0 casi siempre gana el más probable, y con 1 o más las opciones menos probables salen seguido. Cómo funciona el muestreo por dentro (top-p, top-k y la distribución completa) está en Modelos de IA.

El muestreo no es la única fuente de variación. Hay tres:

  1. El muestreo. Explicado arriba. Se controla con la temperatura y, en algunos proveedores, con una semilla (seed): un número que fija la secuencia de azar.
  2. La versión del modelo. Los proveedores actualizan sus modelos. Si tu código pide «el modelo más reciente» por su alias, la misma pregunta puede cambiar de respuesta de un mes a otro sin que tú cambies nada. Por eso se fija la versión exacta.
  3. El contexto. Un cambio pequeño en la entrada (otra palabra en la plantilla, los fragmentos de documento en otro orden, un mensaje anterior distinto) cambia la salida. Para el modelo no hay «la misma pregunta» si cambió cualquier cosa del texto que lee.

Aun con temperatura 0 y semilla fija, la salida puede variar un poco: los servidores procesan muchos pedidos juntos en paralelo y eso altera, en el último decimal, algunos cálculos internos. La temperatura 0 reduce la variación, pero no la convierte en una garantía.

En la terminal

El mismo pedido cinco veces

Vas a mandar el mismo pedido a tu modelo local cinco veces con temperatura 1 y cinco veces con temperatura 0 y semilla fija, y contar cuántas respuestas distintas salen. Necesitas Ollama con llama3.2:3b (capítulo 1) y Python; el script usa solo la biblioteca estándar. Guarda este programa como variabilidad.py:

import json, urllib.request

URL = "http://localhost:11434/v1/chat/completions"
MODELO = "llama3.2:3b"
PEDIDO = ("En una sola frase: una clienta tiene vencida una factura de US$ 30,00 "
          "y pide la reconexión, que cuesta US$ 5,00. ¿Cuánto paga hoy?")

def llamar(temperatura, semilla=None):
    cuerpo = {"model": MODELO, "temperature": temperatura,
              "messages": [{"role": "user", "content": PEDIDO}]}
    if semilla is not None:
        cuerpo["seed"] = semilla
    pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                    headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(pedido) as r:
        return json.load(r)["choices"][0]["message"]["content"].strip()

for temperatura, semilla in [(1.0, None), (0.0, 42)]:
    respuestas = [llamar(temperatura, semilla) for _ in range(5)]
    print(f"\ntemperatura={temperatura} semilla={semilla}: "
          f"{len(set(respuestas))} respuestas distintas de 5")
    for texto in respuestas:
        print(" -", texto[:120])

Qué observar: con temperatura 1 salen varias redacciones y, a veces, montos distintos. Con temperatura 0 y semilla fija, casi siempre sale la misma respuesta las cinco veces; si sale bien, sale bien siempre, y si sale mal, también sale mal siempre. La temperatura baja quita variación, no errores. El paso 3 muestra la tercera fuente: un cambio en el texto cambia la salida. Los números exactos cambian según el modelo y la computadora; la misma API funciona con un proveedor comercial cambiando la dirección y la clave.

El modelo como «base de datos conversacional» frente a la base relacional

Una forma útil de pensar un LLM dentro de una aplicación es como una base de datos conversacional: algo a lo que le preguntas en lenguaje natural y te responde con lo que «sabe». La comparación sirve justamente porque muestra lo que el modelo no es.

Imagínalo así

Una base de datos relacional es un archivador con fichas numeradas: si pides la ficha 20417, te da exactamente esa, la misma hoy y mañana, o te dice que no existe. Un modelo es un bibliotecario que leyó todo el edificio: si le preguntas por un cliente, te cuenta algo plausible aunque nunca haya visto su ficha, y te lo cuenta con otras palabras cada vez.

Una base de datos relacional (relational database) guarda los datos en tablas con columnas y tipos fijos. Se consulta con SQL (Structured Query Language, lenguaje de consulta estructurado), que dice qué se quiere y no cómo buscarlo. La búsqueda es por coincidencia exacta (igual, mayor, entre, empieza con), las escrituras son transacciones ACID (Atomicity, Consistency, Isolation, Durability: atomicidad, consistencia, aislamiento y durabilidad) y el resultado es repetible: la misma consulta sobre los mismos datos da el mismo resultado.

Un modelo guarda lo que aprendió repartido en sus parámetros (weights), millones o miles de millones de números ajustados en el entrenamiento. No hay filas ni claves: se le pregunta con texto, busca por parecido de significado y responde generando. Lo que no está en sus parámetros ni en el contexto, lo completa con lo más plausible. Esa es la alucinación (hallucination): una respuesta fluida y falsa.

La conclusión práctica es una regla de arquitectura: la verdad del negocio vive en los sistemas deterministas (la base de facturación, el CRM, el motor de tarifas) y el modelo se usa para lo que hace bien: entender lenguaje, resumir, clasificar, redactar y decidir qué consultar. Cuando necesita un dato exacto, lo pide a un sistema por medio de una herramienta, en lugar de recordarlo.

Cuándo hace falta determinismo: cálculos, cumplimiento, auditoría y flujos repetibles

No todo pide determinismo. Un borrador de correo, un resumen de una llamada o tres ideas para una campaña pueden salir distintos cada vez y está bien: una persona los revisa. El problema aparece cuando la salida del modelo entra en un proceso que espera un dato exacto. Hay cuatro casos típicos:

  • Cálculos. Montos, saldos, prorrateos, impuestos, fechas de vencimiento. Un modelo puede sumar bien muchas veces y mal una; con dinero, una vez es demasiado. La regla: el modelo nunca hace la cuenta final.
  • Cumplimiento. Lo que se le dice a un cliente sobre sus derechos, una tarifa o un contrato tiene consecuencias legales. La respuesta debe salir de un texto aprobado y poder citarlo.
  • Auditoría. Si alguien pregunta en seis meses por qué el asistente dijo algo, hay que poder mostrar exactamente qué entró y qué salió. Sin determinismo, al menos hace falta un registro completo.
  • Flujos repetibles. Cuando la salida es la entrada de otro programa (clasificar un ticket para enrutarlo, extraer los datos de una factura), el programa siguiente necesita siempre la misma forma: los mismos campos, los mismos nombres y las mismas unidades.

Para el asistente de atención, Lucía y Mateo hicieron una tabla simple con cada salida del asistente y una columna: «¿qué pasa si sale distinto?». Los resúmenes de tickets quedaron como «no importa, lo revisa el agente». El monto a pagar y la categoría del ticket quedaron como «importa siempre». Esa columna decide cuántas capas de envoltorio lleva cada salida.

Las capas del envoltorio: parámetros, plantillas, esquemas, contexto verificado, herramientas y validadores

La solución no es cambiar el modelo, sino envolverlo. El patrón de este capítulo es un envoltorio determinista (deterministic wrapper) alrededor de un núcleo probabilístico: capas de código normal que fijan lo que entra, restringen lo que sale y comprueban el resultado.

Imagínalo así

Una planta embotelladora no le pide a cada operario que llene las botellas «más o menos hasta arriba». Pone una boquilla que mide el volumen, un molde que da siempre la misma forma, una etiqueta impresa y una báscula al final de la línea que separa las botellas que no pesan lo correcto. El líquido es el mismo; lo que cambia es todo lo que lo rodea.

Las capas, de adentro hacia afuera:

  1. Parámetros. Temperatura baja (entre 0 y 0,2 para salidas que importan), un máximo de tokens (max tokens) para cortar respuestas largas, secuencias de parada (stop sequences), semilla cuando el proveedor la ofrece y la versión exacta del modelo fijada en la configuración.
  2. Plantillas. El mismo texto de instrucciones, en el mismo orden, con variables que llena el código. Una plantilla versionada (respuesta-agente@v3) evita que dos partes del programa le pidan lo mismo al modelo con palabras distintas. El capítulo 4 la construye.
  3. Esquemas. Se le pide al modelo un JSON que cumpla un esquema JSON (JSON Schema): qué campos, de qué tipo y con qué valores permitidos. Muchos proveedores, y Ollama, pueden forzar la salida a ese esquema. Con eso el programa siguiente siempre recibe la misma forma. El capítulo 5 está dedicado a esto.
  4. Contexto verificado. El modelo responde con documentos aprobados y vigentes, no con su memoria. Si la política de reconexión dice US$ 5,00, ese texto va en el contexto. Lo construyen los capítulos 4 y 8.
  5. Herramientas. Todo dato exacto o cálculo lo hace un sistema determinista: el modelo pide calcular_total(cuenta=20417) y el motor de tarifas responde 35,00. El capítulo 9 las construye.
  6. Validadores. Código que revisa la salida antes de usarla: que el JSON cumpla el esquema, que el monto coincida con el de la herramienta, que cada cita exista en el documento citado. Si algo falla, se reintenta o se escala.

Cada capa ataca una fuente de error distinta, y por eso no se reemplazan entre sí. La temperatura 0 no arregla un monto inventado, porque el modelo inventa el mismo monto todas las veces. El esquema garantiza la forma, pero no que el número sea correcto. El contexto verificado arregla los hechos, pero no las sumas. El laboratorio lo muestra con los mismos veinte pedidos de Mateo.

Separar planear, que hace el modelo, de ejecutar, que hace el código

La capa de herramientas lleva a una idea que ordena toda la arquitectura del curso: el modelo planea y el código ejecuta. El modelo es bueno para entender un pedido desordenado («hola, se me pasó la de octubre y quiero que me vuelvan a conectar hoy, cuánto es») y convertirlo en un plan estructurado: la acción es reconectar, la cuenta es la 20417, hay una factura vencida. El código es bueno para todo lo demás: consultar el saldo real, aplicar la tarifa vigente, sumar, verificar permisos y ejecutar.

Imagínalo así

En un restaurante, el mesero escucha al cliente («algo liviano, sin gluten, que no tarde») y lo convierte en una comanda clara: «ensalada 4, sin crutones, mesa 7». La cocina no interpreta deseos: cocina la comanda. Y la caja no le pregunta al mesero cuánto cuesta la ensalada: la busca en el sistema. El modelo es el mesero; la cocina y la caja son el código.

En la práctica, el plan del modelo es un JSON con esquema, por ejemplo {"accion": "reconectar", "cuenta": 20417}. El código lo valida, llama al motor de tarifas y obtiene el total. Si hace falta una respuesta en lenguaje natural, se le pasa al modelo el número ya calculado y se le pide solo la redacción («dile a la clienta que el total es US$ 35,00 y por qué»). El número nunca sale de la imaginación del modelo.

En la terminal

El modelo planea, el código calcula

Vas a pedirle al modelo solo el plan, con un esquema JSON obligatorio, y a calcular el monto en Python con una tabla de tarifas. Usa la API propia de Ollama, que acepta el esquema en el campo format (la versión compatible con OpenAI lo hace con response_format, como verás en el capítulo 5). Guarda este programa como planear.py:

import json, urllib.request

URL = "http://localhost:11434/api/chat"
TARIFAS = {"factura": 30.00, "reconexion": 5.00}  # la fuente de verdad
ESQUEMA = {
    "type": "object",
    "properties": {
        "accion": {"type": "string",
                   "enum": ["reconectar", "consultar_saldo", "otra"]},
        "facturas_vencidas": {"type": "integer"},
    },
    "required": ["accion", "facturas_vencidas"],
}
MENSAJE = ("Hola, se me pasó la factura de octubre y quiero "
           "que me reconecten hoy. ¿Cuánto es?")

cuerpo = {
    "model": "llama3.2:3b", "stream": False, "format": ESQUEMA,
    "options": {"temperature": 0},
    "messages": [
        {"role": "system",
         "content": "Clasifica el pedido de la clienta. Devuelve solo el JSON pedido."},
        {"role": "user", "content": MENSAJE},
    ],
}
pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                headers={"Content-Type": "application/json"})
with urllib.request.urlopen(pedido) as r:
    plan = json.loads(json.load(r)["message"]["content"])

print("Plan del modelo:", plan)
if plan.get("accion") != "reconectar" or plan.get("facturas_vencidas", 0) < 1:
    print("El plan no pasa la validación: se escala a una persona.")
else:
    total = plan["facturas_vencidas"] * TARIFAS["factura"] + TARIFAS["reconexion"]
    print("Total calculado por el código: US$", f"{total:.2f}".replace(".", ","))

Verificar, reintentar o escalar a una persona

Un validador que encuentra un error tiene tres salidas, y elegir bien entre ellas es parte del diseño:

  • Reparar. Si el error es de forma (falta una coma en el JSON, un campo viene como texto en vez de número), a veces se arregla con código sin volver a llamar al modelo.
  • Reintentar. Se vuelve a llamar al modelo, idealmente con el error en el mensaje: «tu respuesta no cumple el esquema: falta el campo facturas_vencidas». Conviene un tope (uno o dos reintentos), porque cada reintento cuesta tiempo y dinero, y si el modelo falló tres veces en lo mismo, la cuarta probablemente también.
  • Escalar. La respuesta pasa a una persona con todo lo que se intentó. Es la salida correcta cuando el error es de contenido y no de forma: el monto no coincide, la cita no existe o el pedido no encaja en ningún plan conocido.
Imagínalo así

Un cajero automático que no puede leer tu tarjeta te pide que la vuelvas a meter, una o dos veces. Si sigue sin leerla, no inventa tu saldo: se la queda y te dice que vayas a la ventanilla. Reintentar un poco y después escalar es más seguro que adivinar.

Para el asistente, Mateo escribió la regla en una línea de configuración: dos reintentos para errores de esquema, ninguno para errores de monto (esos se escalan directo) y un aviso en el panel del agente cuando el asistente no está seguro. La tasa de escalamiento se volvió un número del tablero: si sube, algo cambió en el modelo, en la plantilla o en los datos. El capítulo 17 lo convierte en una métrica.

Registrar todo para poder reproducir una respuesta

Si una respuesta no se puede repetir con exactitud, al menos tiene que poder reconstruirse. Para cada llamada al modelo el registro guarda:

  • el identificador del pedido y quién lo hizo;
  • el modelo y su versión exacta, la temperatura, la semilla y el máximo de tokens;
  • la plantilla con su versión y los valores de sus variables;
  • el contexto que entró: qué fragmentos de qué documentos, en qué orden;
  • las herramientas llamadas, con sus entradas y salidas;
  • la salida del modelo, el resultado de cada validador, los reintentos y si se escaló;
  • los tokens, el costo y el tiempo de cada paso.

Con eso, cuando la jefa de reclamos pregunta por qué el asistente le dijo algo raro a un agente el jueves pasado, Mateo puede abrir el registro, ver exactamente qué entró y volver a correr la misma llamada para estudiarla. A esta forma de registrar se la llama traza (trace), y cada paso dentro de ella es un tramo (span). El registro contiene datos de clientes, así que tiene sus propios permisos, plazos de retención y enmascarado. El capítulo 17 construye las trazas con detalle.

La idea clave

Envoltorio determinista alrededor de un núcleo probabilístico. El modelo entiende, planea y redacta; el código fija lo que entra, restringe la forma de lo que sale, hace los cálculos, verifica el resultado y registra todo. Cada capa ataca un error distinto: la temperatura, el azar; el esquema, la forma; el contexto, los hechos; las herramientas, los cálculos; los validadores, lo que se escapó.

Pruébate

Pruébate

Nombra las tres fuentes de variación de un modelo de lenguaje.

El muestreo (controlado por la temperatura y, a veces, una semilla), los cambios de versión del modelo y los cambios en el contexto (plantilla, orden de los fragmentos, historia de la conversación).

Con temperatura 0, el modelo responde US$ 30,00 todas las veces a la pregunta de Carmen. ¿Qué capa del envoltorio falta?

La temperatura quitó la variación, pero el error es de hechos o de cálculo: faltan el contexto verificado (la tarifa de reconexión) o, mejor, la herramienta que calcula el total.

¿Por qué se fija la versión exacta del modelo en la configuración?

Porque un alias como «el más reciente» puede cambiar de modelo sin aviso, y la misma pregunta empezaría a responderse distinto sin que el equipo cambie nada.

En «el modelo planea, el código ejecuta», ¿qué produce cada parte en el caso de la reconexión?

El modelo produce un plan estructurado (acción reconectar, cuenta, facturas vencidas); el código lo valida, consulta las tarifas, calcula el total y, si hace falta, le pasa el número al modelo solo para redactar.

Un validador encuentra que el monto del texto no coincide con el de la herramienta. ¿Reintenta o escala?

Escala: es un error de contenido, no de forma. Reintentar sirve para errores de esquema; con montos, adivinar otra vez no es seguro.

Nombra cuatro cosas que debe guardar el registro para reconstruir una respuesta.

Cualquiera de estas: modelo y versión, parámetros (temperatura, semilla, máximo de tokens), plantilla y versión con sus variables, contexto que entró, herramientas con entradas y salidas, salida, resultado de los validadores, reintentos, tokens, costo y tiempos.
