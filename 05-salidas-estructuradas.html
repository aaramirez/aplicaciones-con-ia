Salidas estructuradas y esquemas JSON

Una respuesta bien escrita le sirve a una persona; a un programa le sirve un dato con nombre, tipo y valores permitidos. Este capítulo arma la versión 0.3 del asistente de atención, que clasifica cada ticket y extrae los datos de las facturas en JSON que el código valida antes de usar.

Prosa frente a datos: por qué un programa necesita estructura

La jefa del equipo de reclamos tenía un pedido concreto para la versión 0.3: que el asistente, además de responder, clasificara cada ticket nuevo para mandarlo a la cola correcta. El ticket T-55190 dice: «Me cobraron dos veces los US$ 30,00 de septiembre en la cuenta 20417. Es la segunda vez que llamo y nadie me resuelve». Mateo le pidió al modelo la categoría y recibió: «Este ticket parece corresponder a un problema de facturación, específicamente un cobro duplicado, y la clienta se nota molesta». Una persona lo entiende al instante. El programa que enruta tickets no sabe qué hacer con esa frase.

Imagínalo así

Una carta y un formulario pueden decir lo mismo. La carta («le escribo porque el mes pasado me cobraron dos veces…») es fácil de escribir y difícil de procesar: alguien tiene que leerla y entenderla. El formulario tiene casillas con nombre: motivo, cuenta, monto. Un empleado nuevo puede procesar cien formularios en una mañana; cien cartas, no. Una salida estructurada es pedirle al modelo que llene el formulario en vez de escribir la carta.

Mateo intentó primero el camino corto: buscar en el texto la palabra «duplicado» con una expresión regular (regular expression). Funcionó con ese ticket y falló con los siguientes, que decían «doble cobro», «me cobraron de más» o «dos cargos iguales». Cada arreglo agregaba un caso y rompía otro. El problema no era la expresión regular, sino pedirle a un programa que entienda prosa.

La solución es que el modelo devuelva datos: un objeto con campos fijos, tipos fijos y valores elegidos de una lista. Para el ticket de Carmen:

{"categoria": "cobro_duplicado", "cuenta": "20417", "factura": "F-87102",
 "monto_reclamado": 30.00, "moneda": "USD", "urgencia": "alta",
 "resumen": "Reclama un cobro duplicado de la factura de septiembre; segundo contacto."}

Con eso, el código enruta a la cola de facturación sin leer prosa, cuenta los reclamos por categoría y compara el monto con el sistema de facturación. El patrón de este capítulo es ese: el modelo produce datos que el código valida.

JSON Schema en lo esencial

Para pedir datos hay que decir qué forma tienen. El estándar para eso es JSON Schema (esquema JSON): un documento, también en JSON, que describe qué campos lleva un objeto, de qué tipo es cada uno y qué valores acepta. Los proveedores de modelos, Ollama y las bibliotecas de validación lo entienden.

Imagínalo así

El esquema es el molde de una galleta. No dice de qué sabor es la masa, pero garantiza la forma: todas salen con el mismo tamaño y el mismo borde. Si una sale torcida, se nota al compararla con el molde.

Este es el esquema clasificacion-ticket@v1 del asistente:

{
  "type": "object",
  "properties": {
    "categoria": {"type": "string",
                  "enum": ["cobro_duplicado", "reconexion", "visita_tecnica",
                           "cambio_de_plan", "otro"]},
    "cuenta":    {"type": "string", "pattern": "^[0-9]{5}$"},
    "factura":   {"type": ["string", "null"], "pattern": "^F-[0-9]{5}$"},
    "monto_reclamado": {"type": ["number", "null"], "minimum": 0},
    "moneda":    {"type": "string", "enum": ["USD"]},
    "urgencia":  {"type": "string", "enum": ["baja", "media", "alta"]},
    "resumen":   {"type": "string", "maxLength": 200}
  },
  "required": ["categoria", "cuenta", "factura", "monto_reclamado",
               "moneda", "urgencia", "resumen"],
  "additionalProperties": false
}

Con seis palabras clave se cubre casi todo:

  • type: el tipo (string, number, integer, boolean, object, array o null). Una lista como ["number", "null"] acepta los dos: «un número o nada».
  • properties y required: los campos y cuáles no pueden faltar.
  • enum: la lista cerrada de valores permitidos.
  • pattern: una expresión regular que el texto debe cumplir, como cinco dígitos para la cuenta.
  • minimum, maxLength y afines: límites de números y textos.
  • additionalProperties: false: prohíbe campos que no estén en la lista. Sin esto, el modelo puede agregar un campo "sentimiento" que nadie pidió y que algún programa termine usando.

Hay mucho más en el estándar (objetos anidados, listas con items, referencias con $ref), pero un esquema para un modelo conviene que sea plano y corto: cada nivel de anidamiento y cada campo opcional es una oportunidad más de que el modelo se confunda.

Modo JSON, salidas estructuradas del proveedor y decodificación restringida

Hay tres formas de pedirle JSON a un modelo, y cada una garantiza más que la anterior.

  1. Pedirlo en las instrucciones. «Responde solo con un JSON con los campos…». No garantiza nada. Los modelos grandes cumplen casi siempre; los pequeños a veces envuelven el JSON en un bloque de Markdown con tres comillas invertidas, agregan «¡Claro! Aquí está:» o dejan una coma de más.
  2. Modo JSON (JSON mode). Un parámetro de la API ("response_format": {"type": "json_object"} en la API compatible con OpenAI) que garantiza que la salida sea JSON válido. No garantiza qué campos trae ni con qué valores.
  3. Salidas estructuradas (structured outputs). Se manda el esquema completo y el proveedor garantiza que la salida lo cumpla: los campos requeridos, los tipos y los valores de enum. En la API compatible con OpenAI es "response_format": {"type": "json_schema", "json_schema": {...}}; en la API propia de Ollama, el campo format que usaste en el capítulo 2.

¿Cómo puede un proveedor garantizar algo en un modelo probabilístico? Con la decodificación restringida (constrained decoding). En cada paso, antes de elegir el siguiente token, el motor mira qué tokens mantendrían la salida dentro del esquema y pone en cero la probabilidad de todos los demás. Si el modelo ya escribió {"categoria": ", los únicos tokens permitidos son los que empiezan alguno de los cinco valores del enum. «Cobro», con mayúscula, o «doble» quedan fuera: el modelo no los puede elegir aunque los prefiera.

Imagínalo así

Un cajero automático no te deja escribir letras en el campo del monto: el teclado solo tiene números. No es que confíe en que vas a escribir bien; es que no hay otra forma de escribir. La decodificación restringida le quita al modelo las teclas que lo sacarían del esquema.

Dos advertencias importantes. La primera: la decodificación restringida garantiza la forma, no la verdad. Si el escaneo de una factura dice «F-882I3» con una I mayúscula y el esquema exige dígitos, el modelo está obligado a escribir un dígito, y puede escribir «F-88243», que cumple el esquema y es falso. La segunda: no todos los motores aplican todas las palabras clave (pattern y maxLength, por ejemplo, tienen soporte desigual). Por las dos razones, el código vuelve a validar todo lo que recibe.

Clasificar un ticket con un esquema

Vas a pedirle a tu modelo local la clasificación del ticket T-55190 con salida estructurada por la API compatible con OpenAI, y a revisarla con un validador mínimo en Python. El esquema de la práctica es más simple que el del texto: sin nulos ni pattern, que el código revisa después. Guarda el programa como clasificar.py:

import json, re, urllib.request

URL = "http://localhost:11434/v1/chat/completions"
CATEGORIAS = ["cobro_duplicado", "reconexion", "visita_tecnica", "cambio_de_plan", "otro"]
ESQUEMA = {
    "type": "object",
    "properties": {
        "categoria": {"type": "string", "enum": CATEGORIAS},
        "cuenta": {"type": "string"},
        "monto_reclamado": {"type": "number"},
        "urgencia": {"type": "string", "enum": ["baja", "media", "alta"]},
        "resumen": {"type": "string"},
    },
    "required": ["categoria", "cuenta", "monto_reclamado", "urgencia", "resumen"],
}
TICKET = ("Me cobraron dos veces los US$ 30,00 de septiembre en la cuenta 20417. "
          "Es la segunda vez que llamo y nadie me resuelve.")

def validar(d):
    errores = [f"falta {c}" for c in ESQUEMA["required"] if c not in d]
    if d.get("categoria") not in CATEGORIAS:
        errores.append(f"categoria fuera de la lista: {d.get('categoria')!r}")
    if not re.fullmatch(r"[0-9]{5}", str(d.get("cuenta", ""))):
        errores.append(f"cuenta no tiene 5 dígitos: {d.get('cuenta')!r}")
    if not isinstance(d.get("monto_reclamado"), (int, float)):
        errores.append("monto_reclamado no es un número")
    return errores

cuerpo = {
    "model": "llama3.2:3b", "temperature": 0,
    "response_format": {"type": "json_schema",
                        "json_schema": {"name": "clasificacion_ticket", "schema": ESQUEMA}},
    "messages": [
        {"role": "system", "content": "Clasifica el ticket de atención. Devuelve solo el JSON."},
        {"role": "user", "content": TICKET},
    ],
}
pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                headers={"Content-Type": "application/json"})
with urllib.request.urlopen(pedido) as r:
    texto = json.load(r)["choices"][0]["message"]["content"]

print("Salida del modelo:", texto)
try:
    datos = json.loads(texto)
except json.JSONDecodeError as e:
    print("No es JSON válido:", e)
else:
    errores = validar(datos)
    if errores:
        print("Errores:", errores)
    else:
        print("Válida: se enruta a la cola de", datos["categoria"])

  2. Cambia TICKET por «¿Puedo cambiar la fecha de la visita del jueves? Mi cuenta es 40981.» (el ticket T-55204 de Ana) y vuelve a ejecutar.
  3. Borra la línea de "response_format" (las dos líneas que ocupa) y ejecuta otra vez con el ticket de Carmen.

Qué observar: con el esquema, la salida siempre es un JSON con los cinco campos y una categoría de la lista: json.loads nunca falla. Con el ticket de Ana la categoría cambia a visita_tecnica y el monto suele salir en 0, porque el esquema obliga a poner un número aunque no haya monto: por eso el esquema del texto acepta null. Sin response_format, un modelo pequeño puede responder con un bloque de Markdown, con texto antes del JSON o con otra categoría escrita a su manera, y el programa tiene que lidiar con eso. Los resultados exactos cambian según el modelo.

Validar en el código con Zod o Pydantic

Aunque el proveedor garantice el esquema, el código valida otra vez. Hay tres razones: el modelo de respaldo puede no soportar salidas estructuradas, algunas palabras clave no se aplican en todos los motores y, sobre todo, hay reglas que un esquema JSON no puede expresar. En lugar de escribir el validador a mano, como en la práctica, se usa una biblioteca. Las dos más comunes son Pydantic en Python y Zod en TypeScript.

# Python con Pydantic
from typing import Literal, Optional
from pydantic import BaseModel, Field

class Clasificacion(BaseModel):
    categoria: Literal["cobro_duplicado", "reconexion", "visita_tecnica", "cambio_de_plan", "otro"]
    cuenta: str = Field(pattern=r"^\d{5}$")
    factura: Optional[str] = Field(default=None, pattern=r"^F-\d{5}$")
    monto_reclamado: Optional[float] = Field(default=None, ge=0)
    urgencia: Literal["baja", "media", "alta"]
    resumen: str = Field(max_length=200)

esquema = Clasificacion.model_json_schema()        # el JSON Schema que va al modelo
dato = Clasificacion.model_validate_json(texto)    # lanza ValidationError si no cumple
// TypeScript con Zod
import { z } from "zod";

const Clasificacion = z.object({
  categoria: z.enum(["cobro_duplicado", "reconexion", "visita_tecnica", "cambio_de_plan", "otro"]),
  cuenta: z.string().regex(/^\d{5}$/),
  factura: z.string().regex(/^F-\d{5}$/).nullable(),
  monto_reclamado: z.number().nonnegative().nullable(),
  urgencia: z.enum(["baja", "media", "alta"]),
  resumen: z.string().max(200),
}).strict();

const r = Clasificacion.safeParse(JSON.parse(texto));   // r.success o r.error.issues

La ventaja principal es tener una sola definición. De la clase de Pydantic sale el esquema que se manda al modelo y el validador que revisa la respuesta; si alguien agrega un campo, cambian los dos a la vez. El esquema tiene versión, igual que la plantilla (capítulo 4): clasificacion-ticket@v1, y la traza guarda cuál se usó.

Después de la validación de forma viene la validación de negocio, que ningún esquema expresa: que la cuenta exista, que la factura citada sea de esa cuenta, que el monto reclamado no supere el de la factura, que la urgencia «alta» venga acompañada de un motivo. Esas reglas consultan los sistemas de la empresa y son las que separan un JSON bien formado de un dato en el que se puede confiar.

Rechazar, reparar o reintentar
El capítulo 2 presentó las tres salidas de un validador. Con datos estructurados, la elección depende de en qué capa falló la salida, y se puede automatizar casi por completo:
  • Falla de sintaxis: no es JSON válido. Las causas típicas son mecánicas: el JSON viene envuelto en un bloque de Markdown, trae texto antes o después, o tiene una coma final. Se repara con código, sin volver a llamar al modelo: quitar las comillas invertidas, recortar desde la primera llave hasta la última, quitar la coma. Si después de reparar sigue sin ser JSON, se reintenta.
  • Falla de esquema: es JSON, pero falta un campo, sobra otro, un tipo no coincide o un valor no está en el enum. Se reintenta con el error en el mensaje: «tu respuesta no cumple el esquema: monto_reclamado debe ser un número, recibí "treinta"». Uno o dos reintentos como máximo (capítulo 3). Con salidas estructuradas del proveedor, esta falla casi desaparece.
  • Falla de negocio: el JSON cumple el esquema, pero el dato no cuadra con la realidad: la factura F-88214 no es de la cuenta 20417, o el monto reclamado es de US$ 300,00 sobre una factura de US$ 30,00. Se rechaza y se escala a una persona. Reintentar aquí es pedirle al modelo que adivine otra vez, y un número adivinado dos veces no es más confiable.
Hay un detalle que conecta con el capítulo 3: con streaming, el JSON llega por partes y no se puede validar hasta el final. Por eso el asistente usa streaming para la explicación que lee el agente y espera completa la salida estructurada. Algunas bibliotecas validan JSON parcial mientras llega, pero la decisión de usarlo se toma con el objeto entero.


Enumeraciones, unidades e identificadores canónicos
Un esquema bien hecho no solo da forma: elimina las ambigüedades que después cuestan horas de limpieza de datos. Tres decisiones lo logran.
Enumeraciones (enums) en lugar de texto libre. Si la categoría es texto libre, en un mes habrá «cobro duplicado», «Cobro doble», «doble cargo» y «facturación - duplicado», y el tablero de reclamos mostrará cuatro barras para lo mismo. Con un enum, hay un solo valor: cobro_duplicado. Los valores van en minúsculas, sin tildes ni espacios, porque son identificadores para programas, y siempre incluyen una salida como otro: sin ella, el modelo mete a la fuerza un ticket raro en la categoría más parecida. El panel muestra a las personas una etiqueta bonita («Cobro duplicado»); el dato guarda el identificador.
Unidades explícitas. «30» puede ser dólares, centavos o días. El esquema separa el número de su unidad (monto_reclamado y moneda), y las fechas van en ISO 8601 (2026-11-05), nunca como «05/11/2026», que en un país es 5 de noviembre y en otro, 11 de mayo. En el código, el dinero no se guarda como número de punto flotante, que no representa exactamente 0,10: se convierte a un decimal exacto (Decimal en Python) o a centavos enteros (3000) apenas pasa la validación.
Identificadores canónicos. La cuenta es siempre un texto de cinco dígitos ("20417", no 20417 como número, que perdería un cero inicial) y la factura siempre F- más cinco dígitos. Y la regla más importante: el modelo no inventa identificadores. Puede copiar uno que aparece en el texto del ticket o elegir uno de una lista que le da el contexto, pero el código comprueba que exista en el sistema antes de usarlo. Un identificador con la forma correcta y que no existe es el error más difícil de ver a simple vista.


Extraer datos de documentos: facturas, contratos y formularios
La otra mitad de la v0.3 es la extracción (extraction): convertir un documento en un JSON. Los agentes reciben fotos de facturas, comprobantes de pago y formularios de cambio de plan, y hoy copian los datos a mano. Es uno de los usos más rentables de un modelo, y uno de los más traicioneros.
Imagínalo así
Pasar una factura a una planilla es un trabajo que un practicante hace bien, pero nadie le deja la caja sin revisar: el contador mira que las líneas sumen el total y que el número de factura exista en el sistema. El modelo es un practicante muy rápido; las validaciones son el contador.
El recorrido tiene cuatro pasos:
  1. Leer el documento. Si es un PDF con texto, se extrae el texto; si es una foto o un escaneo, pasa por OCR o por un modelo de visión (capítulo 3). La calidad de la imagen decide buena parte del resultado: una «I» que parece un «1», una coma que desaparece y convierte 30,00 en 3000.
  2. Extraer con esquema. Se pide el JSON con un esquema factura@v1: número, cuenta, periodo, fechas, líneas con concepto y monto, y total. Conviene pedir también un campo de confianza por documento o por campo, o una lista de campos que el modelo no pudo leer.
  3. Validar las reglas internas del documento. Las líneas suman el total; la fecha de vencimiento es posterior a la de emisión; el número de factura cumple el patrón. Estas reglas detectan muchos errores de lectura sin consultar a nadie.
  4. Cruzar con los sistemas. Si la factura es de la empresa, el sistema de facturación tiene la verdad: el número existe, es de esa cuenta y tiene ese total. Lo que no cuadra va a una cola de revisión humana (human review queue) con el documento y el JSON lado a lado.
Lo mismo vale para contratos (partes, fechas, plazos, cláusulas de permanencia) y formularios (cada casilla con su campo). En todos los casos el esquema dice qué buscar, las reglas internas detectan lo imposible y el cruce con los sistemas detecta lo falso.

Extraer una factura y comprobar que suma
Vas a extraer los datos de una factura a partir de su texto, como lo dejaría un OCR con un error típico, y a validar en el código que las líneas sumen el total y que el número exista en una tabla de facturación de ejemplo. Guarda el programa como extraer.py:
import json, re, urllib.request
from decimal import Decimal

URL = "http://localhost:11434/v1/chat/completions"
TEXTO_OCR = """FACTURA N.º F-88213        Cuenta: 20417
Periodo: octubre 2026       Emisión: 01/10/2026   Vence: 05/11/2026
Plan Hogar 200 ........................ 25,42
Impuestos ............................. 4,58
TOTAL A PAGAR US$ ..................... 3O,OO"""
FACTURACION = {"F-88213": {"cuenta": "20417", "total": Decimal("30.00")}}
ESQUEMA = {
    "type": "object",
    "properties": {
        "numero": {"type": "string"}, "cuenta": {"type": "string"},
        "vencimiento": {"type": "string", "description": "AAAA-MM-DD"},
        "lineas": {"type": "array", "items": {"type": "object",
                   "properties": {"concepto": {"type": "string"}, "monto": {"type": "number"}},
                   "required": ["concepto", "monto"]}},
        "total": {"type": "number"},
    },
    "required": ["numero", "cuenta", "vencimiento", "lineas", "total"],
}
cuerpo = {
    "model": "llama3.2:3b", "temperature": 0,
    "response_format": {"type": "json_schema",
                        "json_schema": {"name": "factura", "schema": ESQUEMA}},
    "messages": [
        {"role": "system", "content": "Extrae los datos de la factura. Las fechas del "
         "documento están en formato día/mes/año; devuélvelas como AAAA-MM-DD. "
         "Los montos usan coma decimal."},
        {"role": "user", "content": TEXTO_OCR},
    ],
}
pedido = urllib.request.Request(URL, data=json.dumps(cuerpo).encode("utf-8"),
                                headers={"Content-Type": "application/json"})
with urllib.request.urlopen(pedido) as r:
    f = json.loads(json.load(r)["choices"][0]["message"]["content"])
print(json.dumps(f, ensure_ascii=False, indent=2))

problemas = []
suma = sum(Decimal(str(l["monto"])) for l in f["lineas"])
total = Decimal(str(f["total"]))
if suma != total:
    problemas.append(f"las líneas suman {suma} y el total dice {total}")
if not re.fullmatch(r"F-[0-9]{5}", f["numero"]):
    problemas.append(f"número con formato inválido: {f['numero']}")
real = FACTURACION.get(f["numero"])
if real is None:
    problemas.append("la factura no existe en facturación")
elif real["cuenta"] != f["cuenta"] or real["total"] != total:
    problemas.append("no coincide con facturación (cuenta o total)")
if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", f["vencimiento"]) or f["vencimiento"] != "2026-11-05":
    problemas.append(f"vencimiento dudoso: {f['vencimiento']} (debería ser 2026-11-05)")
print("Problemas:", problemas or "ninguno, se registra la factura")

La suma usa Decimal y no números de punto flotante para que 25,42 + 4,58 dé exactamente 30,00.
Un caso real
La extracción que parecía perfecta. Un equipo de una empresa de servicios automatizó la carga de facturas de proveedores con un modelo y salidas estructuradas. Durante dos meses, el 100 % de las salidas fue JSON válido y el tablero mostraba cero errores. Una conciliación contable encontró la diferencia: un proveedor emitía sus facturas con fechas en formato mes/día, y el sistema había registrado varias con el vencimiento equivocado, lo que generó pagos con recargo. El esquema garantizaba la forma de la fecha, no cuál era. La corrección agregó dos reglas de negocio (vencimiento posterior a la emisión y dentro de un plazo razonable) y una cola de revisión para los proveedores nuevos. El indicador de «JSON válido» dejó de ser el número del tablero; lo reemplazó el porcentaje de facturas que pasan el cruce con contabilidad.
En la práctica
La v0.3 del asistente. El asistente clasifica cada ticket nuevo con el esquema clasificacion-ticket@v1 antes de que un agente lo abra, y el sistema de tickets lo enruta con el campo categoria. Lo que no pasa la validación de negocio queda en la cola general, como antes. En una muestra de 400 tickets revisados por la jefa de reclamos, 352 quedaron en la categoría correcta, 31 cayeron en otro (casi todos consultas mixtas) y 17 se equivocaron; ninguno de los 17 tenía una factura o un monto que no cuadrara, porque esos se rechazaban. La extracción de facturas empezó solo con las facturas propias de la empresa, que se pueden cruzar con facturación: las de terceros esperan a tener un buen conjunto de pruebas (capítulo 16). Con eso, el nivel 1 del asistente tiene sus tres piezas: llama al modelo con control (v0.1), responde con contexto y cita (v0.2) y produce datos que el código valida (v0.3).


La idea clave
Salidas estructuradas: el modelo produce datos que el código valida. El esquema JSON fija la forma, con enumeraciones, unidades e identificadores canónicos; las salidas estructuradas del proveedor y la decodificación restringida la garantizan; Pydantic o Zod la vuelven a comprobar desde una sola definición; y las reglas de negocio, que consultan los sistemas, deciden si el dato es verdadero. Lo sintáctico se repara, lo de esquema se reintenta y lo de negocio se rechaza.


Pruébate
Pruébate
¿Qué garantiza el modo JSON que no garantiza pedirlo en las instrucciones, y qué no garantiza?
Garantiza que la salida sea JSON válido. No garantiza qué campos trae, de qué tipo ni con qué valores: para eso hacen falta las salidas estructuradas con esquema.
¿Para qué sirve additionalProperties: false?
Prohíbe campos que no están en el esquema, para que el modelo no agregue datos que nadie pidió y que algún programa termine usando.
La decodificación restringida obliga a que la factura tenga el patrón F- y cinco dígitos. ¿Por qué igual hay que cruzarla con facturación?
Porque garantiza la forma, no la verdad: si el escaneo era ilegible, el modelo puede escribir un número con la forma correcta que no existe o que es de otra cuenta.
La salida viene envuelta en un bloque de Markdown con tres comillas invertidas. ¿Reparar, reintentar o rechazar?
Reparar con código: es una falla de sintaxis mecánica; se quitan las comillas o se recorta desde la primera llave hasta la última, sin volver a llamar al modelo.
¿Por qué la cuenta se define como texto de cinco dígitos y no como número?
Porque es un identificador, no una cantidad: como número podría perder ceros iniciales, y como texto con patrón se valida exactamente.
En una factura extraída, las líneas suman US$ 29,70 y el total dice US$ 30,00. ¿Qué tipo de regla lo detectó y qué se hace?
Una regla interna del documento (las líneas suman el total). La factura no se registra: va a la cola de revisión humana, y si es de la empresa se cruza con facturación.
