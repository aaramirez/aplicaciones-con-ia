Exponer el asistente como API REST con los lineamientos de referencia

Imagínalo así

En un banco, cualquier ventanilla recibe el mismo formulario de depósito, con los mismos campos en el mismo orden. No importa qué cajero te atienda ni en qué sucursal estés: el formulario es el contrato. Si cada ventanilla inventara el suyo, nadie sabría qué llenar.

Hasta aquí, el asistente tenía un solo cliente: el panel al costado de la pantalla de tickets. Para que lo usen otros equipos tiene que comportarse como cualquier servicio de la empresa, con una API REST (Representational State Transfer, el estilo de API que usa recursos y los verbos de HTTP) que siga las mismas reglas que las demás. El curso Backend y APIs presenta algunos lineamientos de referencia; aplicados al asistente, se ven así:

  • Recursos en plural y la versión en la ruta: POST /api/v1/consultas, GET /api/v1/operaciones/{id}. La ruta corta /v1/consultas que usó el curso pasa a la forma completa.
  • JSON en camelCase: sinEvidencia, traceId, montoTotal.
  • Un sobre para el éxito: la respuesta va dentro de data, sin campos redundantes como success.
  • Un sobre para el error: error con code, message, details y traceId, para que quien llama pueda reaccionar sin leer texto libre.
  • Dinero sin decimales flotantes: los montos van como texto decimal con su moneda ("35.00", "USD"), porque 0.1 + 0.2 no da 0.3 en coma flotante.

Los códigos de estado (status codes) dicen lo que pasó sin abrir el cuerpo. Una API con IA usa los de siempre, con algunos significados propios:

CódigoCuándo lo devuelve el asistente
200 OKRespuesta lista, incluida la abstención («no lo sé» es una respuesta válida)
202 AcceptedRecibió una tarea larga o una acción que espera aprobación
401 / 403Sin token, o la persona no tiene permiso sobre ese ticket o esa cuenta
422La entrada no cumple el contrato, o una clave de idempotencia repetida con otro cuerpo
429Se agotó el límite de peticiones o el presupuesto
503El modelo principal y el de respaldo no responden

Antes de escribir código, el contrato se escribe en OpenAPI, el formato estándar para describir una API REST. Con él se generan la documentación y los clientes, y la batería del capítulo 19 prueba contra él.

SSE para la respuesta en streaming y 202 Accepted para las operaciones largas

Hay dos situaciones en las que el par «pregunta y respuesta» de HTTP no alcanza.

Imagínalo así

En un restaurante, la sopa llega en cuanto está y el plato fuerte después: no esperas a que todo esté listo para empezar a comer. Y si pides una torta de cumpleaños para el sábado, no te quedas parado en el mostrador hasta el sábado: te dan un número de pedido y pasas a buscarla, o te llaman cuando está.

Cuando la respuesta tarda unos segundos, conviene mostrarla mientras se escribe, como en el capítulo 3. Para eso se usa SSE (Server-Sent Events, eventos enviados por el servidor): el cliente pide con Accept: text/event-stream y el servidor mantiene abierta la respuesta y manda eventos de texto, cada uno con un nombre y sus datos. El asistente usa cuatro: delta (un pedazo de la respuesta), fuente (una cita confirmada), fin (con el traceId y el uso de tokens) y error. SSE es HTTP común en un solo sentido, del servidor al cliente; pasa por los mismos proxies y balanceadores, y el navegador se reconecta solo. Un WebSocket (canal de dos vías sobre una sola conexión) solo hace falta si el cliente también tiene que mandar datos mientras recibe, como en la voz del capítulo 6.

Una regla nace de los guardrails (guardrails, los controles en código sobre lo que entra y sale del modelo): el texto que sale por delta todavía no pasó el guardrail de salida, que necesita la respuesta completa. Por eso el panel lo muestra como borrador, el evento fin confirma, y si el guardrail bloquea, llega un evento error que reemplaza el borrador.

Cuando la tarea tarda minutos o espera a una persona, mantener la conexión abierta es mala idea. La API responde 202 Accepted: «recibí el pedido y lo voy a procesar». En el encabezado Location va la dirección de una operación (operation) que el cliente consulta cuando quiera, con su estado: en-curso, esperando-aprobacion, terminada o fallida. Así funcionan el informe del agente de avería masiva, que recorre 340 tickets, y el reembolso que espera a la supervisora. Si el cliente no quiere preguntar cada tanto, se registra un webhook (webhook, una URL del cliente a la que el servidor avisa cuando termina).

En la terminal

Una respuesta por partes y una operación que se consulta

Vas a levantar una API local de juguete con las dos formas de responder y a probarlas con curl. No necesitas Ollama: el modelo está simulado para que veas el protocolo. Guarda este programa como api_local.py:

import json, threading, time, uuid
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

OPERACIONES = {}
RESPUESTA = "Carmen debe US$ 35,00: la factura F-88213 más el cargo de reconexión."

def informe(op_id):
    time.sleep(8)  # el agente revisa los tickets de la avería
    OPERACIONES[op_id] = {"id": op_id, "estado": "terminada",
                          "resultado": {"ticketsRevisados": 340, "visitasNecesarias": 23}}

class Api(BaseHTTPRequestHandler):
    def enviar_json(self, estado, cuerpo, extra=None):
        datos = json.dumps(cuerpo, ensure_ascii=False).encode("utf-8")
        self.send_response(estado)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("X-Trace-Id", uuid.uuid4().hex[:6])
        for k, v in (extra or {}).items():
            self.send_header(k, v)
        self.end_headers()
        self.wfile.write(datos)

    def evento(self, nombre, datos):
        self.wfile.write(f"event: {nombre}\ndata: {json.dumps(datos, ensure_ascii=False)}\n\n".encode("utf-8"))
        self.wfile.flush()

    def do_POST(self):
        self.rfile.read(int(self.headers.get("Content-Length", 0)))
        if self.path == "/api/v1/consultas":
            if "text/event-stream" not in self.headers.get("Accept", ""):
                return self.enviar_json(200, {"data": {"respuesta": RESPUESTA,
                                              "fuentes": ["politica-reconexion-2026"]}})
            self.send_response(200)
            self.send_header("Content-Type", "text/event-stream; charset=utf-8")
            self.send_header("Cache-Control", "no-cache")
            self.end_headers()
            for palabra in RESPUESTA.split(" "):
                self.evento("delta", {"texto": palabra + " "})
                time.sleep(0.25)  # el modelo escribe
            self.evento("fuente", {"id": "politica-reconexion-2026"})
            self.evento("fin", {"traceId": uuid.uuid4().hex[:6], "tokensSalida": 21})
        elif self.path == "/api/v1/analisis-averia":
            op_id = f"op-{len(OPERACIONES) + 1:04d}"
            OPERACIONES[op_id] = {"id": op_id, "estado": "en-curso"}
            threading.Thread(target=informe, args=(op_id,), daemon=True).start()
            self.enviar_json(202, {"data": OPERACIONES[op_id]},
                             {"Location": f"/api/v1/operaciones/{op_id}"})
        else:
            self.enviar_json(404, {"error": {"code": "NO_EXISTE", "message": self.path}})

    def do_GET(self):
        op = OPERACIONES.get(self.path.rsplit("/", 1)[-1])
        if not self.path.startswith("/api/v1/operaciones/") or op is None:
            return self.enviar_json(404, {"error": {"code": "NO_EXISTE", "message": self.path}})
        self.enviar_json(200, {"data": op})

    def log_message(self, *args):
        pass

print("API en http://127.0.0.1:8791 (Ctrl+C para salir)", flush=True)
ThreadingHTTPServer(("127.0.0.1", 8791), Api).serve_forever()

  1. Compara la primera respuesta, un solo JSON dentro de data, con la segunda, que llega palabra por palabra.
  2. En la tercera, busca el código 202 y el encabezado Location.
  3. Consulta la operación enseguida y otra vez a los diez segundos. Detén la API con Ctrl+C.

Qué observar: con Accept: text/event-stream la respuesta llega en eventos delta y termina con fuente y fin; la opción -N le dice a curl que no espere el final para mostrar. El informe no bloquea a nadie: el 202 vuelve al instante con la dirección de la operación, que pasa de en-curso a terminada con su resultado. Es el mismo contrato que usaría el panel de tickets con el asistente real. Si el puerto 8791 está ocupado, cámbialo en el programa y en los comandos.

Cómo se opera un modelo propio en producción está en IA en producción, y el despliegue y el monitoreo en general, en DevOps.

El plan técnico de 12 meses

Imagínalo así

Una mudanza grande no se hace en un día. Primero se contrata el camión y se consiguen las cajas, después se embala por cuartos, se lleva lo esencial, se instala la cocina antes de traer las visitas, y recién al final se cuelgan los cuadros. Si cuelgas los cuadros antes de que lleguen las paredes, no tienes dónde colgarlos.

El plan técnico es el orden en que se construyen las piezas, con lo que tiene que estar listo para pasar a la siguiente etapa. El plan de adopción de la empresa (presupuesto, personas, comunicación y la decisión de seguir o cerrar cada piloto) está en Pilotos que escalan. Este es el de ingeniería:

Dos dependencias se rompen con frecuencia. La primera: empezar el nivel 3 antes de tener servidores MCP de facturación y órdenes, y terminar escribiendo integraciones a mano que después hay que tirar. La segunda: dejar la revisión de seguridad para después del piloto del agente, cuando el agente ya tiene permisos de escritura.

Principios de operación: empezar angosto, el modelo más pequeño, humano en el bucle y cambios reversibles

Cuatro principios resumen cómo se opera todo lo anterior, y valen para cualquier área:

  • Empezar angosto. Un equipo, un tipo de consulta, una métrica con línea base. El asistente empezó con diez agentes y tres temas, no con los 90 agentes y todos los temas.
  • El modelo más pequeño que alcanza. Se elige con la batería, no con la intuición, y el enrutador del capítulo 14 manda a un modelo más grande solo lo que lo necesita. Cada respuesta cuesta menos y llega antes.
  • Humano en el bucle donde importa. No en todo, porque nadie aprueba mil cosas por día con atención, sino en lo irreversible, en lo caro y en lo nuevo. La política del capítulo 11 decide dónde.
  • Cambios reversibles. Los prompts, los modelos y los umbrales se cambian por configuración, con versión, detrás de un interruptor y con la posibilidad de volver atrás en minutos. Un cambio que no se puede deshacer necesita más revisión que uno que sí.
En la práctica

El portal de clientes, sin escribir un asistente nuevo. El equipo del portal integró el asistente en tres semanas. No construyó RAG, ni memoria, ni trazas: consumió POST /api/v1/consultas con SSE y su propio token de servicio, con un alcance distinto. Para el canal de clientes se agregó una versión de la plantilla con otro tono, un filtro que deja fuera los documentos internos y una regla en la política: desde el portal no se proponen reembolsos, solo se abre un ticket. La batería sumó 40 casos del canal nuevo, incluidos los intentos de inyección directa que en el panel interno eran raros. El piloto empezó con el 5 % de las visitas del portal.

Riesgos y ética

Este curso trató la seguridad, la privacidad de los datos en el contexto y en los registros, y el control de las acciones. Hay otra familia de riesgos que no se resuelve con código: el sesgo en las decisiones que el asistente ayuda a tomar, la transparencia con los clientes sobre cuándo les responde una IA, los derechos sobre los textos generados y la regulación que ya alcanza a algunos usos. Una empresa que lleva la IA a todas sus áreas necesita una evaluación de impacto para cada caso y un responsable que la firme. Todo eso es el tema de IA responsable, y conviene leerlo antes de abrir un asistente a los clientes, no después.

Un caso real

Avisar que hay una IA. Varios marcos regulatorios recientes, entre ellos la Ley de IA europea, piden que una persona sepa cuándo está conversando con un sistema de IA y no con otra persona. Para el asistente interno es fácil: los agentes lo saben. Para el portal de clientes, el equipo agregó una línea fija al abrir la conversación, una marca en cada respuesta generada y la opción de pedir una persona en cualquier momento. Son tres cambios de interfaz, pero salen de una decisión que no es técnica.

La idea clave
Un camino por niveles, cada uno con su arquitectura, sus KPIs y su plan. El asistente se integra como cualquier servicio, con una API REST predecible, SSE para mostrar la respuesta mientras se escribe y 202 Accepted para lo que tarda o espera a una persona. Pruébate
Pruébate
¿Por qué la respuesta «no lo sé» del asistente se devuelve con 200 OK y no con un código de error?
Porque es una respuesta válida y esperada: el servicio funcionó y decidió abstenerse por falta de evidencia. Los códigos de error son para cuando el pedido no se pudo atender (entrada inválida, sin permiso, modelo caído).
¿Cuándo conviene SSE y cuándo 202 Accepted?
SSE, cuando la respuesta tarda segundos y se quiere mostrar mientras se escribe. 202 Accepted, cuando la tarea tarda minutos o espera a una persona: se devuelve la dirección de una operación que el cliente consulta o que avisa por webhook.
¿Por qué el texto que llega en los eventos delta se muestra como borrador?
Porque el guardrail de salida necesita la respuesta completa para revisarla. El evento fin la confirma; si el guardrail la bloquea, un evento error reemplaza el borrador.
Un equipo quiere empezar el nivel 3 en el mes 6, pero los servidores MCP de facturación estarán listos en el mes 7. ¿Qué riesgo corre?
Escribir integraciones a mano con facturación para no esperar, que después hay que tirar o mantener en paralelo, y llegar al nivel 3 sin el control de permisos que da el servidor MCP.
Nombra los cuatro principios de operación del capítulo.
Empezar angosto, el modelo más pequeño que alcanza, humano en el bucle donde importa (lo irreversible, lo caro y lo nuevo) y cambios reversibles (por configuración, con versión y con vuelta atrás).
